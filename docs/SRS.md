# Software Requirements Specification (SRS)

## 1. Project Information

**Project Name:** Siriraj Smart Outpatient Referral System for Hematology (OPD Only)

**Document Type:** Software Requirements Specification

**Version:** 0.3

**Date:** 2026-07-29 (v0.3 — ปรับตามมติอาจารย์รอบที่ 2 ดู [PROPOSAL_REVIEW.md](PROPOSAL_REVIEW.md) §0 และ §8)

**Prepared For:** ภาควิชาอายุรศาสตร์ สาขาโลหิตวิทยา โรงพยาบาลศิริราช

## 2. Purpose

เอกสารนี้กำหนดความต้องการของระบบคัดกรองและส่งต่อผู้ป่วยนอกทางไกลสำหรับคลินิกโลหิตวิทยา โดยเริ่มจากเครื่องมือที่ใช้งานได้เร็วและดูแลง่าย ได้แก่ Google Form, Google Sheet, LINE และหน้า web กลาง เพื่อให้แพทย์ พยาบาล และเจ้าหน้าที่สามารถรับเรื่อง คัดกรอง ติดตามสถานะ และประสานงาน refer ได้เป็นระบบมากขึ้น ภายใต้ข้อกำหนดด้านความปลอดภัยและ PDPA

ระบบนี้เป็นระบบสนับสนุน workflow การส่งต่อผู้ป่วย OPD เท่านั้น ไม่ใช่ระบบวินิจฉัยโรค ไม่ใช่ระบบเวชระเบียนหลัก และไม่แทนการตัดสินใจทางคลินิกของแพทย์

## 3. Background

การส่งต่อผู้ป่วยมายัง OPD Hematology มีปริมาณมาก และมักมีปัญหาเอกสารไม่ครบ การคัดกรองไม่เป็นระบบ การกระจายภาระงานไม่สมดุล และการติดตามกลับใช้เวลามาก ระบบที่เสนอนี้ต้องช่วยลดงานซ้ำซ้อน ลดการตกหล่น เพิ่มความชัดเจนของสถานะ และทำให้ผู้เกี่ยวข้องทุกฝ่ายเข้าถึงข้อมูลที่จำเป็นได้ง่าย โดยยังคงมีเจ้าหน้าที่หรือแพทย์ตรวจสอบก่อนยืนยันนัดหมาย

## 4. Goals

1. รับ refer OPD Hematology ผ่านช่องทางที่เข้าถึงง่าย
2. จัดเก็บข้อมูลและเอกสารประกอบอย่างเป็นระบบ
3. คัดกรองและแยกประเภท case ตามกลุ่มงาน Hematology
4. กระจายงานให้แพทย์ พยาบาล และเจ้าหน้าที่อย่างตรวจสอบได้
5. แจ้งเตือนสถานะผ่าน LINE โดยไม่เปิดเผยข้อมูลสุขภาพเกินจำเป็น
6. มีหน้า web กลางที่ใช้งานง่ายสำหรับทุก role
7. รองรับหลัก PDPA ตั้งแต่การเก็บ ใช้ เปิดเผย เข้าถึง เก็บรักษา และลบข้อมูล

## 5. Scope

### 5.1 In Scope

- ผู้ป่วยนอก OPD Hematology ที่มีใบส่งตัวหรือมีการส่งต่อเพื่อประเมินนัดหมาย
- คัดกรองงานออกเป็น **4 กลุ่มตามลักษณะงาน** (ไม่ใช่ตามกลุ่มโรค) ดูรายละเอียดใน §8.1
- Google Form สำหรับรับข้อมูล refer
- Google Sheet สำหรับเก็บข้อมูลและติดตามสถานะในระยะ MVP
- Google Drive สำหรับจัดเก็บเอกสารแนบแบบจำกัดสิทธิ์
- LINE Official Account หรือ LINE group workflow สำหรับแจ้งเตือนและส่ง link
- หน้า web กลางสำหรับเข้าใช้งานระบบ ดูคู่มือ ส่ง refer และเข้าถึง dashboard
- Dashboard สำหรับเจ้าหน้าที่ แพทย์ พยาบาล และผู้ดูแลระบบ
- Audit log ขั้นพื้นฐาน เช่น วันที่รับเรื่อง ผู้เปลี่ยนสถานะ และเวลาตอบกลับ
- PDPA notice, consent/acknowledgement, access control, retention policy และ breach workflow

### 5.2 Out of Scope

- ผู้ป่วยใน IPD
- ระบบ EMR หลัก
- ระบบออกใบนัดหมายอย่างเป็นทางการแทนระบบโรงพยาบาล
- การเชื่อมต่อ HN หรือ appointment API ของโรงพยาบาลในระยะ MVP
- Clinical decision support ที่ให้คำวินิจฉัยหรือคำสั่งรักษาอัตโนมัติ
- การส่งข้อมูลสุขภาพเต็มรูปแบบผ่าน LINE message

## 7. System Overview

ระบบในระยะ MVP จะใช้ Google Workspace เป็นฐานข้อมูลและ workflow หลัก โดยมีหน้า web กลางเป็นจุดเข้าใช้งานเดียว (Single Entry Point) ที่เป็นมิตรกับผู้ใช้

```text
แพทย์ต้นทาง
  -> Web Portal (จุดเข้าเดียว) หรือ LINE OA Rich Menu
  -> เลือก 1 ใน 4 กลุ่มงาน
  -> Google Form ของกลุ่มนั้น
  -> Google Sheet + Google Drive
  -> Apps Script Automation (referral ID, triage, SLA, duplicate check)
  -> LINE Notification (batch 10:00 น. / fast-track ทันที)
  -> Staff / Resident / Fellow Dashboard
```

### 7.1 Component Summary

| Component | Purpose |
| --- | --- |
| Web Portal | จุดเข้าใช้งานเดียว เลือกกลุ่มงาน ดู checklist เอกสาร พิมพ์แบบฟอร์มรับทราบ และเข้า dashboard |
| LINE Official Account | ทางเข้าคู่ขนานสำหรับแพทย์ที่ใช้มือถือเป็นหลัก — Rich Menu ตรงกับ 4 กลุ่มบนหน้าเว็บ |
| Google Form | รับข้อมูลผู้ป่วยและเอกสารแนบ แยกฟอร์มตามกลุ่มงาน |
| Google Sheet | เก็บข้อมูล refer, สถานะ, assignment, timestamp |
| Google Drive | เก็บไฟล์แนบโดยใช้ folder permission แบบจำกัดสิทธิ์ |
| Apps Script | สร้าง referral ID, ส่งแจ้งเตือน, validate field, ตรวจเคสซ้ำ, คำนวณ SLA แบบเวลาทำการ |
| LINE Notify | แจ้งเตือน case ใหม่/ค้าง โดยส่งเฉพาะ referral ID + สถานะ + link (ไม่มีข้อมูลสุขภาพ) |
| Dashboard | แสดง queue แยกตามกลุ่มงาน, status, workload, alert level และเคสที่สงสัยซ้ำ |

### 7.2 Hosting and Deployment

| Item | Decision | Rationale |
| --- | --- | --- |
| Framework | Next.js (App Router) + TypeScript + Tailwind CSS | ทีมใช้อยู่แล้ว |
| Hosting | **Cloudflare Pages** | สอดคล้องกับ infra เดิมของทีม และได้ Cloudflare Access มากั้นหน้า `/dashboard` ด้วยบัญชีองค์กรโดยไม่ต้องเขียนระบบ login เอง (รองรับ PDPA-004) |
| Dashboard access control | Cloudflare Access (Zero Trust) จำกัดตามอีเมลองค์กร | ไม่ต้องเก็บรหัสผ่านเอง |
| Google Sheets integration | เรียก Google Sheets REST API ด้วย service account + JWT ฝั่ง server เท่านั้น | หลีกเลี่ยง `googleapis` SDK ที่หนักเกินสำหรับ edge runtime และห้าม expose credential ใน client (NFR-003) |

ทางเลือกสำรอง: Vercel (รองรับ Next.js เต็มรูปแบบและใช้ `googleapis` SDK ได้ตรง) แต่ต้องเขียนระบบ auth เองด้วย NextAuth + Google OAuth

## 8. Workflow

### 8.1 4-Group Triage Workflow

แกนหลักของระบบคือ **ลักษณะงานที่แพทย์ต้นทางร้องขอ** ไม่ใช่กลุ่มโรค เพราะเป็นตัวกำหนดว่าใครเป็นผู้ดูแลและตอบกลับอย่างไร

| กลุ่ม | ลักษณะงาน | ผู้รับผิดชอบหลังบ้าน | Automation |
| --- | --- | --- | --- |
| 1 | ขอนัดหมายพบแพทย์ Stem Cell Transplantation | แพทย์แอดมิน (จัดคิว fellow) | กึ่งอัตโนมัติ |
| 2 | ขอความเห็นสูตรยาเคมีบำบัด | Resident R2/R3 วอร์ดเคมีบำบัด + Attending อนุมัติ | กึ่งอัตโนมัติ |
| 3 | ขอส่งตัวมาให้ยาเคมีบำบัด/ยากดภูมิ (ต้องการเตียง Admit) | Resident R2/R3 วอร์ดเคโม | กึ่งอัตโนมัติ |
| 4 | Refer ผู้ป่วยนอกด้วยเหตุผลอื่น | ไม่มี — ระบบตอบกลับอัตโนมัติ 100% | อัตโนมัติเต็มรูปแบบ |

**กลุ่มโรค (disease group)** ยังคงเก็บไว้เป็นแกนรอง ใช้กำหนด checklist เอกสารและออกรายงาน แต่ไม่ใช้กำหนดผู้รับผิดชอบ

#### ขั้นตอนร่วมทุกกลุ่ม

1. แพทย์ต้นทางเข้า web portal (หรือ LINE OA Rich Menu) — จุดเข้าเดียว
2. เลือก 1 ใน 4 กลุ่ม หรือกด "ไม่แน่ใจว่าเข้ากลุ่มไหน" เพื่อให้เจ้าหน้าที่ช่วยคัดกรอง
3. อ่าน privacy notice และ checklist เอกสารของกลุ่มนั้น
4. พิมพ์หนังสือรับทราบให้ผู้ป่วยลงนาม เก็บต้นฉบับไว้ที่ต้นทาง (ดู PDPA-002)
5. กรอก Google Form ของกลุ่มนั้นและแนบเอกสาร
6. ระบบสร้าง referral ID อัตโนมัติ และตรวจเคสซ้ำ (FR-014)
7. ระบบแจ้งผู้รับผิดชอบผ่าน LINE ในรอบ batch 10:00 น. ของทุกวันทำการ (FR-013)
8. ผู้รับผิดชอบตามกลุ่มดำเนินการและอัปเดตสถานะ
9. ระบบแจ้งผลกลับแพทย์ต้นทางตามช่องทางที่กำหนด

#### กลุ่มที่ 1 — Stem Cell Transplantation

- แพทย์แอดมินกรอกตารางออกตรวจของ fellow transplant ล่วงหน้าทั้งปีการศึกษา
- นัดผู้ป่วยได้ไม่เกิน **2 คนต่อ fellow 1 คนต่อวันออกตรวจ** เมื่อเต็มระบบขึ้นสีเทาและปิดการนัดเพิ่ม
- ระบบต้องแสดง capacity ของ fellow ทุกคนในวันเดียวกัน เพื่อให้เกลี่ยคิวได้ (FR-012)
- ระบบ notify fellow เมื่อมีผู้ป่วย walk-in ในวันที่แพทย์ต้นทางทำนัด
- คำตอบกลับระบุ: วันที่นัด, ชื่อ-สกุล fellow, ให้มาติดต่อ OPD 700 เวลา 08:00 น., ข้อความที่ต้องเขียนบนหัวใบ refer, ลิงก์ทำบัตรโรงพยาบาลออนไลน์ และ checklist เอกสาร

#### กลุ่มที่ 2 — ขอความเห็นสูตรยาเคมีบำบัด

- Resident R2/R3 อ่านข้อมูลสรุปจากฟอร์มใน dashboard (ไม่ใช่ใน LINE)
- เลือกสูตรยามาตรฐานจาก **Template Library** + comment เพิ่มเติม + เบอร์ติดต่อกลับ (คลังเดียวกันนี้ใช้กับกลุ่มที่ 3 ด้วย)
- ส่งให้อาจารย์ Attending ประจำเดือนตรวจทานและอนุมัติ
- กรณีไม่มีสูตรมาตรฐานตรงกับเคส หรือ Attending ขอแก้ไข ให้ย้อนสถานะกลับเป็น Pending Review พร้อมระบุเหตุผล
- SLA เริ่มนับตั้งแต่ timestamp ที่ฟอร์มถูกส่ง จนถึงสถานะ Advice Sent

#### กลุ่มที่ 3 — ขอส่งตัวมาให้ยาเคมีบำบัด/ยากดภูมิ

- Resident R2/R3 อ่านข้อมูลสรุปและปรึกษาอาจารย์ Attending
- คลิกเลือกคำตอบสำเร็จรูป 2 ทางเลือกหลัก:
  - **นัดดูความพร้อม** — นัดพบ Resident ที่ OPD 700 เพื่อประเมินร่างกายก่อนนอนโรงพยาบาล จากนั้นแจ้ง จนท. OPD 700 ทำนัด
  - **ให้คำแนะนำกลับ** — กรณีประเมินแล้วแพทย์ต้นทางดูแลรักษาต่อได้เอง (ตอบกลับรูปแบบเดียวกับกลุ่มที่ 2)
- **ไม่มีขั้นตอนยืนยันเตียง** — resident เป็นผู้นัดผู้ป่วยมาประเมินความพร้อมที่ OPD 700 และให้คิวเอง ทางออกของกลุ่มนี้จึงมีเพียง 2 ทางข้างต้น (มติอาจารย์ 29 ก.ค. 2569)
- คำแนะนำที่ให้กลับไปต้องถูกบันทึกไว้ใน record เพื่อการตรวจสอบย้อนหลัง

#### กลุ่มที่ 4 — Refer ผู้ป่วยนอกด้วยเหตุผลอื่น

- ระบบตอบกลับอัตโนมัติเต็มรูปแบบ ไม่วิ่งเข้าหน้าจอ resident หรือแพทย์แอดมิน
- แพทย์ต้นทางเขียนใบ refer ให้ผู้ป่วยตามปกติ
- ผู้ป่วยแอด QR code ระบบนัดหมายกลาง (Siriraj Connect) เพื่อทำนัดโดยตรง ได้ใบนัดภายใน 3 วันทำการ
- **ต้องมีช่องทางสำรองทางโทรศัพท์** สำหรับผู้ป่วยที่ไม่มีสมาร์ทโฟนหรือใช้ LINE ไม่ได้
- เนื่องจากไม่มีผู้คัดกรอง หน้าเว็บต้องมีปุ่ม "ไม่แน่ใจว่าเข้ากลุ่มไหน" ให้ติดต่อเจ้าหน้าที่ เพื่อลดความเสี่ยงเคสที่ควรอยู่กลุ่ม 1–3 หลุดมาที่กลุ่มนี้

### 8.2 Status Flow

สถานะรวมของระบบ — แต่ละกลุ่มใช้เพียงบางสถานะ (ดู `STATUSES_BY_TYPE` ใน `src/lib/referral-types.ts`)

| Status | Meaning | ใช้กับกลุ่ม |
| --- | --- | --- |
| Submitted | รับข้อมูลจาก Google Form แล้ว | 1–4 |
| Pending Review | รอผู้รับผิดชอบตรวจความครบถ้วน | 1–3 |
| Incomplete | เอกสารหรือข้อมูลไม่ครบ | 1–3 |
| Slot Reserved | จองคิว fellow แล้ว | 1 |
| Awaiting Attending | รออาจารย์ Attending ตรวจทานและอนุมัติ | 2, 3 |
| Advice Sent | ส่งคำแนะนำ/สูตรยากลับแพทย์ต้นทางแล้ว | 2, 3 |
| Readiness Visit Scheduled | นัดประเมินความพร้อมที่ OPD 700 แล้ว | 3 |
| Appointment Confirmed | ยืนยันวันนัด/เตียงแล้ว | 1, 3 |
| Auto Replied | ระบบตอบกลับอัตโนมัติแล้ว | 4 |
| Rejected / Redirected | ไม่เข้าเกณฑ์หรือควรส่งช่องทางอื่น | 1–3 |
| Closed | ปิด case แล้ว | 1–4 |

สถานะที่ถือว่าจบแล้วและหยุดนับ SLA: Advice Sent, Appointment Confirmed, Auto Replied, Rejected / Redirected, Closed

### 8.3 Fail-Safe and Escalation Matrix

กรอบเวลาตอบกลับรวม (Turnaround Time) ไม่เกิน **3 วันทำการ** (24 ชั่วโมงทำการ) นับจากวันที่แพทย์ต้นทางส่งเข้ามา

> แก้จากเดิม 48 ชั่วโมงทำการ (มติ 29 ส.ค. 2569) เพราะ 48 ชั่วโมงทำการเท่ากับ **6 วันทำงาน**
> ซึ่งยาวกว่าที่ทุกฝ่ายเข้าใจกันสี่เท่า ตัวเลขที่สื่อสารออกไปจึงเปลี่ยนเป็น "วัน"
> เพราะไม่มีใครแปลงชั่วโมงทำการเป็นวันในหัวได้
>
> กรอบนี้ครอบคลุมความล่าช้าจากรอบแจ้งเตือน 10:00 น. อยู่ในตัวแล้ว — เคสที่ส่งหลัง 10:00
> จะได้รับแจ้งเช้าวันรุ่งขึ้นและยังเหลือเวลาราวสองวันทำการ จึงไม่ต้องแยกกรอบเวลา
> ตามช่วงเวลาที่ส่ง (ข้อเสนอ 48/72 ชม. ตกไปด้วยเหตุผลนี้)

| ระดับ | เงื่อนไข | การดำเนินการ |
| --- | --- | --- |
| Yellow Alert | ค้างครบ 2 วันทำการ (16 ชม.ทำการ) | ปักหมุดไฮไลต์เคสไว้บนสุดของ LINE Notify รอบ 10:00 น. |
| Red Alert | ค้างครบ 3 วันทำการ (24 ชม.ทำการ) | แจ้ง resident **และคุณหมอแอดมินกลาง** ทันที เพื่อเข้าตรวจสอบหน้างาน |

หากคุณหมอแอดมินกลางไม่สะดวก ระบบต้องส่งต่อไปยังผู้สำรองที่กำหนดไว้ใน §22 Governance

## 9. Functional Requirements

### FR-001 Web Portal

ระบบต้องมีหน้า web กลางที่เข้าถึงได้ง่ายผ่าน URL เดียว รองรับ mobile และ desktop

หน้า web ต้องมีอย่างน้อย:

- ปุ่มส่ง refer
- ปุ่มตรวจสอบสถานะหรือช่องทางติดต่อ
- ปุ่มเข้าสู่ dashboard สำหรับบุคลากร
- คำแนะนำเอกสารที่ต้องเตรียม
- privacy notice แบบอ่านง่าย
- ช่องทางติดต่อกรณีเร่งด่วนหรือส่งข้อมูลไม่ได้

### FR-002 Google Form Submission

ระบบต้องมี Google Form **ฟอร์มเดียว** แยก 4 กลุ่มด้วย section branching
โดยกำหนด field ที่จำเป็นเป็น required — รายละเอียดระดับสร้างได้จริงอยู่ที่
[FORMS_AND_SHEETS.md](FORMS_AND_SHEETS.md)

ข้อมูลขั้นต่ำ:

- Referral ID อัตโนมัติ และวันที่เวลาส่ง
- **checkbox รับทราบแบบบังคับ ติ๊กครบทุกข้อจึงส่งได้** พร้อมบันทึก timestamp
- ชื่อโรงพยาบาลต้นทาง
- ชื่อแพทย์ผู้ส่งตัว
- **เบอร์ติดต่อกลับ (บังคับ)**
- อายุผู้ป่วยเป็นปี และเพศ
- urgency (Routine / Urgent)
- diagnosis และกลุ่มโรค (กลุ่ม 1–3)
- การรักษาที่ได้รับมาแล้ว (กลุ่ม 1–3)
- สิ่งที่ต้องการปรึกษา (กลุ่ม 2, 3)
- checklist เอกสารที่พร้อมนำมา (กลุ่ม 1)

**ห้ามมีในฟอร์มเด็ดขาด:** ชื่อ-สกุลผู้ป่วย, HN, เลขบัตรประชาชน, วันเดือนปีเกิดแบบเต็ม
และต้องมีข้อความเตือนผู้กรอกไม่ให้พิมพ์ข้อมูลเหล่านี้ลงในช่องข้อความอิสระด้วย

### FR-003 Document Checklist

ระบบต้องมี checklist เอกสารตามกลุ่มโรค เช่น

| Group | Required Documents |
| --- | --- |
| Acute leukemia / SiAML | CBC, bone marrow report, flow cytometry, chromosome, molecular mutation, treatment summary |
| Lymphoma | pathology report, block/slide status, imaging, staging, prior treatment |
| Multiple Myeloma | SPEP, serum free light chain, immunofixation, beta-2 microglobulin, bone marrow, imaging |
| Stem Cell Transplantation | diagnosis, disease status, donor/HLA information, prior treatment, transplant indication |
| Other Hematology | referral letter, essential labs, summary of clinical question |

**ขอบเขตของ checklist:** ระบุเฉพาะรายการที่อยู่ในเอกสารข้อเสนอโครงการที่อาจารย์อนุมัติแล้ว
ไม่แตกรายการเอกสารย่อยรายโรคเพิ่ม (เช่น MDS, MPN, CML) เพราะช่อง `diagnosis`
บอกทีมได้อยู่แล้วว่าเป็นโรคใด และทีมจะขอเอกสารเพิ่มเฉพาะที่จำเป็นเป็นราย ๆ ไป
การมี checklist ยาวเกินไปเพิ่มภาระให้แพทย์ต้นทางโดยไม่จำเป็น

**หมายเหตุ:** กลุ่มโรคใน dropdown ของฟอร์มมี 8 กลุ่ม (รวม MDS, MPN, CML)
เพื่อใช้ทำสถิติและคัดกรอง — แยกจาก checklist เอกสารในตารางนี้

### FR-004 Google Sheet Data Store

ระบบต้องบันทึกข้อมูลจาก Google Form ลง Google Sheet แบบ structured table

Sheet หลักที่ต้องมี:

- `referrals`
- `status_log`
- `assignments`
- `users`
- `triage_rules`
- `document_checklist`
- `notification_log`
- `config`

Google Sheet ต้องไม่ถูกตั้งค่าเป็น public หรือ anyone with link สำหรับข้อมูลจริง

### FR-005 Triage Classification

**กลุ่มงาน (referral type)** มาจากการเลือกของแพทย์ต้นทางบนหน้า portal โดยตรง ไม่ใช่จาก rule — เพราะเป็นเรื่องที่ผู้ส่งเท่านั้นที่รู้ว่าต้องการอะไร

**กลุ่มโรค (disease group)** ระบบต้องช่วยเสนอเบื้องต้นจากคำตอบในฟอร์ม โดยใช้ rule ที่แก้ไขได้ใน Google Sheet

ตัวอย่าง rule:

- ถ้าเลือก stem cell transplant หรือมีคำว่า transplant/HLA/donor ให้เสนอ group: Stem Cell Transplantation
- ถ้ามี acute leukemia/AML/ALL/APL ให้เสนอ group: Acute Leukemia
- ถ้ามี lymphoma/DLBCL/HL/NHL ให้เสนอ group: Lymphoma
- ถ้ามี myeloma/MGUS/plasma cell ให้เสนอ group: Multiple Myeloma

ผลลัพธ์ต้องแสดงเป็น suggested group และต้องให้ผู้ใช้ที่มีสิทธิ์ยืนยันหรือแก้ไขได้

### FR-006 Assignment and Workload

ระบบต้องรองรับการมอบหมาย case ให้แพทย์ พยาบาล หรือเจ้าหน้าที่

ระบบต้องแสดง:

- จำนวน case ต่อผู้รับผิดชอบ
- จำนวน case ต่อกลุ่มโรค
- case ค้างเกิน SLA
- วันที่ต้องติดตาม
- หมายเหตุการส่งต่อ

### FR-007 LINE Notification

ระบบต้องแจ้งเตือนผ่าน LINE เมื่อมีเหตุการณ์สำคัญ

เหตุการณ์ที่ต้องแจ้ง:

- มี case ใหม่
- case ถูกระบุว่า incomplete
- case พร้อม triage
- case ค้างเกิน SLA
- มีการ assign case
- ยืนยันวันนัดหรือแจ้งให้ติดต่อกลับ

ข้อความ LINE ต้องใช้ข้อมูลเท่าที่จำเป็น เช่น referral ID, status, action needed และ link ภายใน หลีกเลี่ยงการส่ง diagnosis, HN, ชื่อผู้ป่วย หรือข้อมูลสุขภาพโดยตรงใน LINE message

### FR-010 Audit Log

ระบบต้องบันทึกการเปลี่ยนแปลงสำคัญ ได้แก่:

### FR-011 Reporting

ระบบต้องออกรายงานอย่างน้อย:

- จำนวน refer รายวัน/รายเดือน
- จำนวน case แยกตามกลุ่มโรค

- turnaround time ตั้งแต่รับเรื่องถึงตอบกลับ
- incomplete rate
- workload ต่อผู้รับผิดชอบ

### FR-012 Single Entry Point and Group Routing

หน้า web portal ต้องเป็นจุดเข้าใช้งานเดียว แสดงปุ่มเลือกกลุ่มงานทั้ง 4 กลุ่ม พร้อมคำอธิบายสั้น ๆ ว่าแต่ละกลุ่มใช้เมื่อใด

ข้อกำหนดเพิ่มเติม:

- ต้องมีปุ่มที่ 5 **"ไม่แน่ใจว่าเข้ากลุ่มไหน"** ให้ติดต่อเจ้าหน้าที่ เพื่อลดความเสี่ยงเคสถูกจัดกลุ่มผิดแล้วหลุดจากระบบติดตาม
- LINE OA Rich Menu ต้องมีหัวข้อตรงกับ 4 กลุ่มบนหน้าเว็บ เพื่อรองรับแพทย์ที่ใช้มือถือเป็นหลัก
- แต่ละกลุ่มต้องมีหน้ารายละเอียดของตัวเอง แสดง checklist เอกสาร ผู้รับผิดชอบ กรอบเวลาตอบกลับ และลิงก์ฟอร์ม
- สำหรับกลุ่มที่ 1 ระบบต้องแสดง capacity ของ fellow ทุกคนในวันเดียวกัน และปิดการนัดเมื่อเต็ม 2 คนต่อ fellow ต่อวัน

### FR-013 Business-Hours SLA and Notification Batching

ระบบต้องนับ SLA เป็น **ชั่วโมงทำการ** (จันทร์–ศุกร์ 08:00–16:00 น. ไม่รวมวันหยุดนักขัตฤกษ์) ไม่ใช่ชั่วโมงปฏิทิน เพื่อไม่ให้เคสที่ยื่นเย็นวันศุกร์ถูกแจ้ง Red Alert ทั้งที่ยังไม่มีใครเห็น

การแจ้งเตือน:

- รวมเคสในรอบ 24 ชั่วโมง แล้วส่ง LINE Notify เข้ากลุ่ม Resident **วันละ 1 ครั้ง เวลา 10:00 น. เท่านั้น** เพื่อปกป้องเวลาเรียนทางวิชาการ
- **ไม่มีช่องทางข้ามรอบสำหรับเคสฉุกเฉิน** เพราะหากเป็นเคสฉุกเฉินจริงจะไม่ใช่การ refer แบบ OPD ตั้งแต่ต้น การเปิดช่องนี้ไว้จะถูกใช้ผิดวัตถุประสงค์ (มติอาจารย์ 29 ก.ค. 2569) — เคสฉุกเฉินให้ใช้ช่องทางส่งต่อฉุกเฉินระหว่างโรงพยาบาลตามปกติ
- ระบบต้องบันทึกจำนวนครั้งที่มีการแจ้งเตือนนอกรอบ 10:00 น. เพื่อใช้เป็น KPI (§23)

### FR-014 Duplicate Detection

ระบบต้องตรวจสอบว่าเคสที่ยื่นเข้ามาอาจซ้ำกับเคสเดิมภายใน 30 วันหรือไม่

เนื่องจากระบบไม่เก็บชื่อและ HN จึงใช้การเทียบแบบไม่ระบุตัวตน:

- **สัญญาณหลัก** — เบอร์ติดต่อของแพทย์ผู้ส่งซ้ำกัน + อายุเท่ากัน + เพศเดียวกัน ภายใน 30 วัน
  (ครอบคลุมกรณีพบบ่อยที่สุด คือแพทย์คนเดิมส่งผู้ป่วยรายเดิมเข้ามามากกว่าหนึ่งกลุ่ม)
- **สัญญาณรอง** — โรงพยาบาลต้นทางเดียวกัน + อายุเท่ากัน + เพศเดียวกัน + กลุ่มโรคเดียวกัน ภายใน 30 วัน
- ระบบ **flag ให้เจ้าหน้าที่ตรวจสอบเท่านั้น ห้าม auto-merge** เพราะสัญญาณเหล่านี้ไม่ยืนยันตัวบุคคล
  และอาจเป็นผู้ป่วยคนละคนที่บังเอิญตรงกัน
- Dashboard ต้องแสดงสัญลักษณ์เตือนบนเคสที่สงสัยว่าซ้ำ พร้อมระบุ referral ID ที่อาจซ้ำกัน
- เจ้าหน้าที่ตรวจสอบโดยติดต่อกลับแพทย์ผู้ส่ง ซึ่งเป็นผู้เดียวที่ทราบว่าเป็นผู้ป่วยรายเดียวกันหรือไม่

### FR-015 Fallback Channel

ระบบต้องแสดงช่องทางติดต่อสำรอง (โทรศัพท์) ไว้บนทุกหน้า เพื่อรองรับกรณี:

- Google Form, Apps Script หรือ LINE ใช้งานไม่ได้ชั่วคราว
- ผู้ป่วยไม่มีสมาร์ทโฟนหรือใช้ LINE ไม่ได้ (โดยเฉพาะกลุ่มที่ 4)
- แพทย์ต้นทางไม่แน่ใจว่าเรื่องเข้ากลุ่มใด

หากระบบล่มเกิน 1 วันทำการ ผู้ดูแลระบบต้องแจ้งเวียนทางอีเมลหรือกลุ่มไลน์แพทย์เครือข่ายว่าให้ใช้ช่องทางโทรศัพท์ชั่วคราว

## 10. Web Usability Requirements

หน้า web ต้องออกแบบให้แพทย์ พยาบาล และเจ้าหน้าที่ใช้งานง่าย โดยไม่ต้องเรียนรู้ระบบนาน

ข้อกำหนด:

- ใช้ภาษาไทยเป็นหลัก และมีคำอังกฤษเฉพาะทางเท่าที่จำเป็น
- รองรับมือถือ เพราะผู้ใช้จำนวนมากเข้าผ่าน LINE
- ปุ่มหลักต้องชัดเจน เช่น ส่ง Refer, เข้า Dashboard, ติดต่อเจ้าหน้าที่
- ไม่ใช้ layout ซับซ้อนหรือเมนูหลายชั้น
- ตัวอักษรอ่านง่ายบนมือถือ
- มีสีสถานะที่เข้าใจง่าย เช่น new, incomplete, urgent, done
- มีหน้า error ที่บอกวิธีติดต่อเมื่อส่งฟอร์มไม่ได้
- ลดการพิมพ์ซ้ำด้วย dropdown, checkbox และ template
- ไม่แสดงข้อมูลผู้ป่วยบนหน้า public web

หลักการสำคัญคือให้สิทธิ์น้อยที่สุดเท่าที่จำเป็นต่อหน้าที่ — resident ควรเห็นเฉพาะเคสกลุ่มที่ตนรับผิดชอบเป็นค่าเริ่มต้น

## 12. PDPA and Privacy Requirements

ข้อมูลผู้ป่วยเป็นข้อมูลสุขภาพ จัดเป็นข้อมูลส่วนบุคคลที่มีความละเอียดอ่อนตาม PDPA มาตรา 26 ดังนั้นระบบต้องออกแบบโดยใช้ privacy by design และ security by design ตั้งแต่เริ่มต้น

ข้อกำหนดในเอกสารนี้เป็น requirement เชิงระบบ ไม่ใช่คำปรึกษากฎหมายขั้นสุดท้าย หน่วยงานควรให้ DPO หรือฝ่ายกฎหมายตรวจ privacy notice, lawful basis, data sharing และ retention policy ก่อนใช้งานจริง

### PDPA-001 Privacy Notice

ก่อนส่งข้อมูล ผู้ใช้ต้องเห็น privacy notice ที่อธิบายอย่างน้อย:

- ใครเป็นผู้ควบคุมข้อมูลส่วนบุคคล
- วัตถุประสงค์การเก็บ ใช้ และเปิดเผยข้อมูล
- ประเภทข้อมูลที่เก็บ
- ผู้ที่อาจเข้าถึงข้อมูล
- ระยะเวลาเก็บรักษา
- สิทธิของเจ้าของข้อมูล
- ช่องทางติดต่อ DPO หรือหน่วยงานรับผิดชอบ
- ข้อจำกัดของการใช้ Google/LINE ในระบบ MVP

### PDPA-002 Lawful Basis and Consent

ระบบใช้ consent **2 ชั้น** เนื่องจากศิริราชไม่ได้พบผู้ป่วยโดยตรงในขั้นตอนนี้ ผู้ที่แจ้งผู้ป่วยได้จริงคือแพทย์ต้นทาง

**ชั้นที่ 1 — Checkbox บังคับใน Google Form** (สำหรับแพทย์ต้นทางผู้กรอก):

> "ข้าพเจ้าในฐานะแพทย์ผู้ส่งต่อ ขอรับรองว่าได้แจ้งผู้ป่วยหรือผู้แทนโดยชอบธรรมให้ทราบแล้วว่า ข้อมูลการรักษาบางส่วนจะถูกส่งผ่านระบบแบบฟอร์มออนไลน์ไปยังศิริราช เพื่อวัตถุประสงค์การประเมินและนัดหมายส่งต่อการรักษา และมีหนังสือรับทราบเก็บไว้ที่ต้นทางแล้ว"

**ชั้นที่ 2 — หนังสือรับทราบสิ่งพิมพ์ให้ผู้ป่วยลงนาม** เก็บต้นฉบับไว้ที่โรงพยาบาลต้นทาง ไม่ต้องส่งกลับมาศิริราช (ลดการเก็บข้อมูลซ้ำซ้อนตาม PDPA-003) — เนื้อหาแบบฟอร์มดูที่หน้า `/consent` ของระบบ

**ข้อควรระวังเรื่องถ้อยคำ:** หนังสือรับทราบใช้คำว่า "รับทราบความเสี่ยงและยินยอมให้ส่งข้อมูล" เท่านั้น **ห้ามใช้ถ้อยคำสละสิทธิ์แบบเหมารวม เช่น "ไม่รับผิดชอบทุกกรณี"** เพราะเมื่อศิริราชรับข้อมูลมาแล้วยังคงมีหน้าที่ในฐานะผู้ควบคุมข้อมูลตาม PDPA-003 ถึง PDPA-007 ซึ่งไม่สามารถให้ผู้ป่วยสละสิทธิ์ล่วงหน้าได้

สำหรับข้อมูลสุขภาพ ต้องให้ DPO/Legal ยืนยันฐานกฎหมายที่เหมาะสม เช่น explicit consent, medical treatment, vital interest, public health หรือฐานอื่นที่เกี่ยวข้องตามบริบทจริง

### PDPA-003 Data Minimization

ระบบต้องเก็บเฉพาะข้อมูลที่จำเป็นต่อการรับ refer และคัดกรองนัดหมาย

ข้อห้าม:

- ห้ามเก็บเลขบัตรประชาชน เว้นแต่มีเหตุผลและฐานกฎหมายชัดเจน
- ห้ามเก็บข้อมูลที่ไม่จำเป็น เช่น ศาสนา การเมือง หรือข้อมูลครอบครัวที่ไม่เกี่ยวกับการรักษา
- ห้ามส่งข้อมูลสุขภาพเต็มรูปแบบใน LINE message
- ห้ามเปิด sheet หรือ drive เป็น public

### PDPA-004 Access Control

ระบบต้องจำกัดสิทธิ์การเข้าถึงด้วยบัญชีองค์กร

ข้อกำหนดขั้นต่ำ:

- ใช้ Google Workspace account ของหน่วยงาน
- เปิดใช้งาน 2-Step Verification ถ้าหน่วยงานรองรับ
- จำกัด Drive folder ตาม role
- จำกัด Google Sheet ให้เฉพาะบุคลากรที่เกี่ยวข้อง
- แยกสิทธิ์ view/edit/admin
- ทบทวนรายชื่อผู้มีสิทธิ์อย่างน้อยทุก 3 เดือน

### PDPA-005 Data Retention

#### หลักการตั้งต้น: ระบบนี้ไม่ใช่ที่เก็บเวชระเบียน

ข้อมูลในระบบนี้เป็น **ข้อมูลประสานงานการส่งต่อ (coordination data)** ไม่ใช่เวชระเบียน
เวชระเบียนตัวจริงอยู่ใน **HIS ของโรงพยาบาล** ทั้งต้นทางและศิริราชอยู่แล้ว
ตามที่ระบุไว้ตั้งแต่ §2 Purpose ว่าระบบนี้ไม่ใช่ระบบเวชระเบียนหลัก

ผลที่ตามมาซึ่งสำคัญต่อการออกแบบ:

- **ไม่ต้องเก็บตามระยะเวลาของเวชระเบียน** เพราะไม่ได้ทำหน้าที่นั้น
- **การลบข้อมูลไม่ทำให้สูญเสียประวัติการรักษาของผู้ป่วย** เพราะ HIS เก็บไว้แล้ว
- **ควรลบเร็ว ไม่ใช่เก็บนาน** — ยิ่งเก็บนานยิ่งเป็นภาระและความเสี่ยงโดยไม่ได้ประโยชน์เพิ่ม

#### ระยะเวลาเก็บรักษา

| ชุด | เนื้อหา | ระยะเวลา | เหตุผล |
| --- | --- | --- | --- |
| **1. เคสเต็ม (กลุ่มที่ 2, 3)** | ข้อมูลที่ส่งเข้ามาทั้งหมด (อายุ เพศ diagnosis stage การรักษา คำถาม เอกสารแนบ ข้อมูลติดต่อแพทย์ต้นทาง) | **1 ปี** นับจากปิดเคส แล้วถอดข้อมูลออกอัตโนมัติ | เป็นข้อมูลประสานงาน ใช้ประโยชน์จริงเฉพาะช่วงที่เคสยังเดินอยู่และช่วงติดตามผลสั้น ๆ |
| **1ก. นัดปลูกถ่าย (กลุ่มที่ 1)** | เหมือนชุดที่ 1 บวกวันนัดและชื่อ fellow | **30 วัน** นับจากวันนัด (มติอาจารย์ 30 ส.ค. 2569) | เคสจบจริงตั้งแต่วันที่ผู้ป่วยมาตามนัด ไม่มีการติดตามต่อในระบบนี้ — และไม่มีใครกดปิดเคส สถานะจึงค้างที่ `Appointment Confirmed` ตลอด ถ้าใช้กฎ "1 ปีนับจากปิดเคส" แถวนี้จะไม่มีวันครบกำหนด |
| **2. คลังคำตอบ** | เฉพาะ "โจทย์ทางคลินิก → คำตอบที่ให้" ถอดข้อมูลที่โยงกลับได้ออกหมด | **ถาวร** | ไม่ใช่ข้อมูลส่วนบุคคลอีกต่อไป และเป็นองค์ความรู้ที่ **HIS ไม่ได้เก็บ** ดูหมายเหตุด้านล่าง |
| **3. สถิติสรุป** | ตัวเลขรวมเท่านั้น เช่น จำนวนเคสต่อเดือนแยกกลุ่ม/โรค/โรงพยาบาลต้นทาง, turnaround time เฉลี่ย, incomplete rate | **ถาวร** | ไม่มีข้อมูลรายบุคคล ใช้ทำรายงานและ KPI ตาม §23 |

#### สิ่งที่ต้องถอดออกเมื่อครบกำหนด (ชุด 1 → ชุด 2)

ไม่ต้องลบทั้งแถว ให้ลบเฉพาะคอลัมน์ที่ทำให้โยงกลับหาตัวผู้ป่วยได้ แล้วย้ายไปชุดที่ 2

| ต้องลบ | เก็บต่อได้ |
| --- | --- |
| `referral_id` (โยงกลับตารางเทียบที่ รพ. ต้นทาง) | ช่วงอายุ (แปลงจากอายุจริง เช่น 40–49) |
| `referrer_org`, `referrer_name`, `referrer_phone` | เพศ |
| `submitted_at` (เหลือเฉพาะปี) | diagnosis, stage, การรักษา |
| เอกสารแนบทั้งหมด | คำถามที่ปรึกษา และ `advice_record` |
| `appointment_date`, `fellow_assigned` (กลุ่มที่ 1) | เหลือแค่ปีกับกลุ่มโรค — พอสำหรับ "ปีนั้นนัดผ่านระบบนี้กี่เคส" |

#### หมายเหตุสำคัญ: ข้อมูลที่ HIS ไม่ได้เก็บ

กลุ่มที่ 2 และกลุ่มที่ 3 บางเคส **ผู้ป่วยไม่ได้มาศิริราชเลย** (ให้คำแนะนำกลับไปแล้วรักษาต่อที่ต้นทาง)
เคสเหล่านี้จึงไม่มีบันทึกใน HIS ของศิริราช

คำแนะนำที่ให้ไปเป็นการกระทำทางคลินิกที่ควรมีร่องรอยไว้ตรวจสอบย้อนหลังได้
จึงต้องเก็บ `advice_record` ไว้ในชุดที่ 2 (แบบถอดชื่อแล้ว) เสมอ —
ซึ่งตอบทั้งเรื่องความรับผิดชอบทางคลินิกและความต้องการย้อนดูเคสเก่าไปพร้อมกัน

#### ข้อกำหนดเพิ่มเติม

- ชุดที่ 2 และ 3 ต้อง**ไม่มี** `referral_id` หรือชื่อโรงพยาบาลต้นทาง มิฉะนั้นจะยังโยงกลับได้และถือเป็นข้อมูลส่วนบุคคลอยู่
- การถอดข้อมูลจากชุดที่ 1 ไปชุดที่ 2 ต้องมีผู้ตรวจทานก่อน เพราะเคสที่หายากมากอาจเดาตัวผู้ป่วยได้จากรายละเอียดทางคลินิกเพียงอย่างเดียว
- เอกสารแนบให้ลบเมื่อปิดเคส ไม่ต้องรอครบ 1 ปี เพราะต้นฉบับอยู่ที่โรงพยาบาลต้นทางและใน HIS อยู่แล้ว
- ระยะเวลาที่แน่นอนของชุดที่ 1 ให้อาจารย์เป็นผู้กำหนดขั้นสุดท้าย

### PDPA-006 Data Sharing

ระบบต้องระบุว่าใครเป็นผู้ควบคุมข้อมูล ผู้ประมวลผลข้อมูล และผู้รับข้อมูล

ต้องพิจารณา:

- Google Workspace terms และ data processing arrangement
- LINE Official Account และข้อจำกัดของการส่งข้อมูลผ่าน LINE
- โรงพยาบาลต้นทางที่ส่งข้อมูล
- บุคลากรภายในที่มีสิทธิ์ดูข้อมูล

### PDPA-007 Breach Response

ต้องมีขั้นตอนรับมือข้อมูลรั่วไหลหรือเข้าถึงผิดสิทธิ์

ขั้นต่ำ:

1. หยุดการเข้าถึงหรือปิด share link ทันที
2. บันทึกเหตุการณ์ วันที่ เวลา ผู้เกี่ยวข้อง และข้อมูลที่ได้รับผลกระทบ
3. แจ้ง admin, DPO และหัวหน้าหน่วยงาน
4. ประเมินความเสี่ยงต่อเจ้าของข้อมูล
5. ดำเนินการแจ้งตามข้อกำหนดกฎหมายและนโยบายหน่วยงาน
6. สรุป root cause และมาตรการป้องกันซ้ำ

## 13. Non-Functional Requirements

### NFR-001 Availability

ระบบ MVP ควรใช้งานได้ในเวลาราชการและรองรับการส่ง form นอกเวลาราชการ โดยต้องมีข้อความชัดเจนว่าไม่ใช่ช่องทาง emergency

### NFR-002 Performance

หน้า web และ Google Form ควรโหลดได้ภายใน 3 วินาทีบนเครือข่ายมือถือทั่วไป

Dashboard ควรแสดงข้อมูล case ล่าสุดได้ภายใน 10 วินาทีหลัง submit form ในกรณีปกติ

### NFR-003 Security

- ต้องใช้ HTTPS
- ห้ามใช้ public link สำหรับ sheet ที่มีข้อมูลผู้ป่วย
- ห้ามฝังข้อมูลลับใน frontend code
- ต้องจำกัด Apps Script owner และ editor
- ต้องแยก production form/sheet ออกจาก test form/sheet

### NFR-004 Backup

ต้องมี backup Google Sheet และไฟล์แนบอย่างน้อยวันละครั้ง หรือใช้ version history / scheduled export ตามความสามารถของ Google Workspace

### NFR-005 Maintainability

workflow, disease group, checklist, SLA และข้อความ notification ต้องแก้ไขได้โดย admin ผ่าน sheet config หรือไฟล์ config โดยไม่ต้องแก้ code ทุกครั้ง

### NFR-006 Accessibility

หน้า web ต้องอ่านง่าย ใช้บนมือถือได้ ปุ่มใหญ่พอ และรองรับผู้ใช้ที่ไม่เชี่ยวชาญคอมพิวเตอร์

## 17. Acceptance Criteria

ระบบ MVP ถือว่าพร้อมทดลองใช้งานเมื่อ:

1. ผู้ส่ง refer สามารถเข้า web portal และส่ง Google Form ได้
2. ข้อมูลเข้า Google Sheet พร้อม referral ID อัตโนมัติ
3. ไฟล์แนบถูกจัดเก็บใน Drive folder ที่จำกัดสิทธิ์
4. เจ้าหน้าที่เห็น case ใหม่ใน dashboard
5. ระบบส่ง LINE notification โดยไม่เปิดเผยข้อมูลสุขภาพเกินจำเป็น
6. ผู้มีสิทธิ์สามารถเปลี่ยน status และบันทึกเหตุผลได้
7. มี privacy notice และ checkbox รับทราบใน form
8. มี access control สำหรับ sheet, drive และ dashboard
9. มี report เบื้องต้นเรื่องจำนวน case และ SLA
10. DPO/Legal ตรวจ requirement ด้าน PDPA ก่อน pilot จริง
11. หน้า portal แสดงปุ่มครบทั้ง 4 กลุ่ม พร้อมปุ่ม "ไม่แน่ใจว่าเข้ากลุ่มไหน" (FR-012)
12. LINE OA Rich Menu มีหัวข้อตรงกับ 4 กลุ่มบนหน้าเว็บ
13. SLA นับเป็นชั่วโมงทำการ และการแจ้งเตือนเกิดขึ้นเฉพาะรอบ 10:00 น. เท่านั้น (FR-013)
14. ระบบ flag เคสที่สงสัยว่าซ้ำได้ และไม่ auto-merge (FR-014)
15. หน้าแบบฟอร์มรับทราบสำหรับผู้ป่วยพิมพ์ออกมาใช้ได้จริง และผ่านการตรวจถ้อยคำจาก DPO
16. เติมรายชื่อผู้รับผิดชอบครบทุกบทบาทตาม §22 Governance รวมถึงผู้สำรองของแอดมินกลาง

## 18. Testing Requirements

### Functional Test

- Submit form สำเร็จ
- Required field ทำงานถูกต้อง
- Upload file สำเร็จ
- Referral ID ไม่ซ้ำ
- LINE notification ส่งสำเร็จ
- Dashboard filter ถูกต้อง
- Status update ถูกบันทึกใน log

### Permission Test

- Public user เปิด sheet ไม่ได้
- Staff ดูเฉพาะข้อมูลที่จำเป็น
- ผู้ไม่มีสิทธิ์เปิด Drive file ไม่ได้
- Admin เท่านั้นที่แก้ config ได้

### Workflow Test (4-Group)

- เลือกกลุ่มที่ 1 แล้วคิว fellow เต็มโควตา 2 คน ระบบต้องปิดการนัดเพิ่มและเสนอ fellow ท่านอื่น
- ยื่นเคสกลุ่มที่ 1 พร้อมกัน 2 รายการในคิวสุดท้ายเดียวกัน ต้องได้ผลลัพธ์ที่ถูกต้องเพียงรายการเดียว (race condition)
- กลุ่มที่ 2: กรณีไม่มีสูตรมาตรฐานตรงเคส ต้องมีเส้นทางส่งต่ออาจารย์โดยตรง
- กลุ่มที่ 2: Attending กด "ขอแก้ไข" ต้องย้อนสถานะกลับพร้อมเหตุผล
- กลุ่มที่ 3: ต้องจบได้เพียง 2 ทาง คือ นัดประเมินความพร้อมที่ OPD หรือ ส่งคำแนะนำกลับ — ไม่มีสถานะรอเตียง
- กลุ่มที่ 4: ผู้ป่วยที่ไม่มี LINE ต้องเห็นช่องทางโทรศัพท์สำรอง

### SLA and Escalation Test

- เคสที่ยื่นเย็นวันศุกร์ต้องไม่ถูกนับ SLA ระหว่างวันหยุด
- เคสค้างครบ 2 วันทำการ ต้องถูกปักหมุดบนสุดของ LINE รอบ 10:00 น.
- เคสค้างครบ 3 วันทำการ ต้องส่ง Red Alert ถึงทั้ง resident และแอดมินกลาง
- แบบฟอร์มต้องไม่มีตัวเลือกระดับ "ฉุกเฉิน" และต้องแสดงข้อความว่าช่องทางนี้ไม่ใช่ช่องทางฉุกเฉิน
- กรณีแอดมินกลางไม่ตอบสนอง ต้องส่งต่อผู้สำรองได้

### PDPA Test

- Privacy notice แสดงก่อน submit
- Form ไม่มี field ที่เก็บข้อมูลเกินจำเป็น
- LINE message ไม่มีข้อมูลสุขภาพละเอียด — ตรวจทุก template ใน §16 ว่ามีเฉพาะ referral ID, กลุ่ม, สถานะ, link
- Sheet/Drive ไม่เป็น public
- มี retention และ deletion procedure
- Checkbox consent เป็น required field ที่ข้ามไม่ได้
- หน้า `/consent` พิมพ์ออกมาแล้วอ่านได้ครบถ้วนบนกระดาษ A4

## 20. Risks and Mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Google Sheet ถูก share ผิด | ข้อมูลรั่วไหล | จำกัดสิทธิ์, review ทุก 3 เดือน, audit sharing |
| ส่งข้อมูลสุขภาพผ่าน LINE | เสี่ยง PDPA | ส่งเฉพาะ referral ID/status/link |
| Form เก็บข้อมูลมากเกินจำเป็น | เสี่ยง compliance | ทบทวน field กับ DPO/แพทย์ |
| ข้อมูลค้างไม่ได้ตอบกลับ | กระทบ service | SLA alert และ dashboard queue |
| ผู้ใช้ไม่เข้าใจ workflow | ใช้งานผิด | web portal เรียบง่ายและมีคู่มือสั้น |
| Sheet โตเกินดูแลยาก | performance/maintenance | วางแผน migrate เป็น web app + database |
| ไม่มี owner ชัดเจน | ระบบไม่ยั่งยืน | ตั้ง admin, clinical owner, DPO contact ตาม §22 |
| แอดมินกลางเป็น single point of failure | Red Alert ไม่มีคนรับ | กำหนดผู้สำรองใน §22 และทดสอบเส้นทางส่งต่อ |
| Resident หมุนเวียนทุกปี | ความรู้ระบบหายไปกับรุ่นเก่า | Rotation Handover Owner อบรมรุ่นใหม่ทุกต้นปีการศึกษา |
| แพทย์ต้นทางเลือกกลุ่มผิด | เคสกลุ่ม 4 หลุดจากระบบติดตามเพราะไม่มีผู้คัดกรอง | ปุ่ม "ไม่แน่ใจว่าเข้ากลุ่มไหน" (FR-012) และคำอธิบายกลุ่มที่ชัดเจน |
| ผู้ป่วยฉุกเฉินถูกส่งผ่านช่องทางนี้ | ล่าช้าเพราะระบบตอบใน 3 วันทำการ | ไม่เปิดตัวเลือกฉุกเฉิน และแจ้งชัดทุกหน้าว่าไม่ใช่ช่องทางฉุกเฉิน |
| ผู้ป่วยไม่มีสมาร์ทโฟน | เข้าไม่ถึงบริการกลุ่มที่ 4 | ช่องทางโทรศัพท์สำรอง (FR-015) |
| Google/LINE ล่ม | รับเรื่องไม่ได้ | BCP ตาม FR-015 แจ้งเวียนใช้โทรศัพท์ชั่วคราว |
| นโยบาย IT ไม่อนุญาตเก็บข้อมูลสุขภาพบน Google | ต้องรื้อสถาปัตยกรรม | ยืนยันกับฝ่าย IT security ก่อนเริ่ม Phase 1 |

### 22.1 บัญชีเจ้าของระบบ

**ระบบต้องอยู่ในบัญชี Google ของหน่วยงาน ไม่ใช่บัญชีส่วนบุคคลของผู้พัฒนา**

เหตุผล:

- เจ้าของระบบตามมติคือ**สาขาวิชาโลหิตวิทยา** การวางระบบไว้ในบัญชีส่วนตัวขัดกับมตินี้
- หากผู้ดูแลย้ายงานหรือเข้าถึงบัญชีไม่ได้ ระบบจะสูญหายทั้งหมด รวมถึง Form, Sheet และ trigger
- อีเมลแจ้งรหัสอ้างอิงที่ส่งจากบัญชีส่วนตัวดูไม่น่าเชื่อถือต่อแพทย์โรงพยาบาลอื่น
- ข้อมูลผู้ป่วยไม่ควรอยู่ในบัญชีส่วนบุคคล ด้วยเหตุผลเดียวกับที่ไม่ใช้เซิร์ฟเวอร์ส่วนตัว
  (ดู [DATA_HOSTING_OPTIONS.md](DATA_HOSTING_OPTIONS.md) §4)

**ต้องย้ายก่อนเปิดใช้จริง** เพราะ Apps Script trigger ผูกกับบัญชีที่สร้างและโอนเจ้าของไม่ได้
ต้องลบแล้วตั้งใหม่ในบัญชีปลายทาง — ยิ่งมีข้อมูลมากยิ่งย้ายยาก

ทางเลือก ตามลำดับความเหมาะสม:

1. บัญชี Google Workspace ของคณะฯ (ดีที่สุด แต่ต้องผ่านฝ่ายสารสนเทศ)
2. บัญชี Google ที่สร้างใหม่ในนามหน่วยงาน โดยเก็บรหัสผ่านไว้กับแพทย์แอดมินกลางและผู้สำรอง
   **ไม่ใช่บุคคลเดียว**

ห้ามใช้บัญชีส่วนตัวของผู้ใดผู้หนึ่งในการเปิดใช้งานจริง
