## 1. สรุปเอกสารต้นทาง

เอกสารกำหนด workflow การคัดกรอง/ส่งต่อผู้ป่วยนอก (OPD Only) แบ่งเป็น **4 กลุ่มตามลักษณะงาน** (ไม่ใช่ตามกลุ่มโรคแบบ SRS.md เดิม):

| กลุ่ม | ลักษณะงาน | ผู้รับผิดชอบหลังบ้าน | ระดับ automation |
| --- | --- | --- | --- |
| 1 | ขอนัดหมายพบแพทย์ Stem Cell Transplantation | แพทย์แอดมิน (จัดคิว fellow, quota 2 คน/fellow/วัน) | กึ่งอัตโนมัติ |
| 2 | ขอความเห็นสูตรยาเคมีบำบัด | Resident R2/R3 ประจำวอร์ดเคมีบำบัด + Attending อนุมัติ | กึ่งอัตโนมัติ |
| 3 | ขอส่งตัวมาให้ยาเคมีบำบัด/ยาภูมิ (ต้องการเตียง Admit) | Resident R2/R3 วอร์ดเคโม | กึ่งอัตโนมัติ |
| 4 | Refer OPD ด้วยเหตุผลอื่น | ไม่มี (fully automated 100%) | อัตโนมัติเต็มรูปแบบ |

กลไกร่วม: แจ้งเตือน LINE Notify แบบ batch ครั้งเดียว 10:00 น. (Time-Protected UI/UX เพื่อปกป้องเวลาเรียนของ resident) และ escalation 2 ระดับ — Yellow Alert (ค้าง 24 ชม.) / Red Alert (ค้าง 48 ชม. แจ้ง resident + คุณหมอแอดมินกลาง)

## 2. จุดแข็ง

- แบ่งกลุ่มตาม workflow-type ทำให้ scope งานของแต่ละ role ชัดเจน ต่างจาก SRS.md เดิมที่แบ่งตามโรคอย่างเดียว
- มี template ข้อความระบบ (LINE, หัวกระดาษใบ refer) ที่ระบุ placeholder ชัดเจน พร้อมใช้งานจริง
- ออกแบบมาเพื่อแก้ปัญหาที่ระบุไว้ตรงจุด: ลดภาระธุรการของแพทย์ต้นทาง และปกป้องเวลาเรียนของ resident (batch notify ครั้งเดียว/วัน)
- มี fail-safe escalation matrix ที่มีเจ้าของชัดเจนในระดับที่ 2 (Red Alert)

## 3. ช่องว่างเชิงระบบ (Cross-Cutting)

### 3.1 ขัดแย้งกับข้อกำหนด PDPA ใน SRS.md เดิม (สำคัญที่สุด)

SRS.md ข้อ PDPA-003 ระบุห้ามส่งข้อมูลสุขภาพเต็มรูปแบบผ่าน LINE message แต่ workflow กลุ่ม 1–3 ในโครงร่างนี้ให้ resident/แพทย์แอดมินอ่านสรุปข้อมูล (ชื่อ-สกุล, diagnosis, treatment, สิ่งที่ต้องการปรึกษา) จาก Google Form แล้วส่งต่อ/สรุปผ่านกลุ่ม LINE Notify ของ resident

**ข้อเสนอ:** เปลี่ยนข้อความแจ้งเตือน LINE ให้เหลือเฉพาะ referral ID + สถานะ + link เข้า dashboard ภายใน (ต้อง login) แทนการพิมพ์ข้อมูลผู้ป่วยลง LINE โดยตรง ต้องให้ DPO/Legal ตรวจก่อน pilot

### 3.2 ไม่มีคำตอบว่าจะเก็บข้อมูลผู้ป่วยไว้บน Google Workspace ได้หรือไม่

เอกสารนี้ (และ SRS.md เดิม open question #1) ยังไม่มีคำยืนยันว่าหน่วยงาน/โรงพยาบาลอนุญาตให้เก็บข้อมูลสุขภาพผู้ป่วยใน Google Form/Sheet/Drive ตาม policy ด้าน IT security ของศิริราชหรือไม่ นี่เป็นความเสี่ยงเชิงองค์กรที่ต้องตอบก่อนเริ่มสร้างจริง ไม่ใช่แค่ประเด็น PDPA เท่านั้น

### 3.3 โครงสร้างข้อมูล/โค้ดปัจจุบันยังไม่ตรงกับ workflow นี้

`mock-referrals.ts` และ dashboard ปัจจุบันจัดกลุ่มตาม **โรค** (Acute Leukemia/Lymphoma/Multiple Myeloma/SCT/Other) และมี status flow แบบ 10 สถานะทั่วไป ไม่ใช่ตาม **4 กลุ่มงาน** ที่เอกสารนี้นิยาม (นัด transplant / consult สูตรยา / ขอ admit / refer อื่น)

**ข้อเสนอ:** ตัดสินใจก่อนว่าจะ (ก) แก้ SRS.md + data model ให้ตรงกับ 4-group นี้ทั้งหมด หรือ (ข) เก็บทั้งสองมิติไว้คู่กัน (workflow-group เป็น field หลัก, disease-group เป็น sub-field) แล้วจึง re-model โค้ด

### 3.4 สถาปัตยกรรมระบบยังไม่ชัดว่า web portal ที่กำลังสร้าง (repo นี้) กับ Google Form ในเอกสารนี้ สัมพันธ์กันอย่างไร

README ของ repo ระบุว่า MVP เป็น Next.js web portal + dashboard แต่เอกสารนี้อ้างอิงการรับข้อมูลผ่าน **Google Form** ล้วนๆ ไม่ชัดว่า:
- แพทย์ต้นทางกรอกข้อมูลผ่านหน้า web ที่สร้างใน repo นี้ หรือกรอกผ่าน Google Form โดยตรง
- ถ้าใช้ Google Form เป็น source of truth แล้ว dashboard ใน repo นี้จะดึงข้อมูลจาก Google Sheet ผ่านช่องทางใด (Apps Script Web App API? Google Sheets API? export CSV?)

**ข้อเสนอ:** ระบุสถาปัตยกรรมให้ชัดในรอบถัดไปของเอกสาร ก่อนลงมือเขียนโค้ดเชื่อมต่อจริง

### 3.5 ไม่มีเจ้าของ/ธรรมาภิบาลระบบ (Governance)

- ไม่ระบุผู้ดูแล "Template Library" สูตรยาเคมีบำบัด และรอบการ review/อัปเดตสูตร
- "คุณหมอแอดมินกลาง" เป็น single point of failure ของ Red Alert — ไม่มีผู้สำรอง (backup contact) เมื่อคุณหมอไม่สะดวก/ลาพัก
- ไม่ระบุว่าใครเป็นเจ้าของระบบโดยรวม (system owner) ต่างจาก SRS.md เดิมที่มีตาราง stakeholders ชัดเจน
- ไม่ระบุผู้ดูแลบัญชี LINE Official Account/Notify (credential, token rotation, rate limit, ค่าใช้จ่ายเมื่อ LINE เปลี่ยนนโยบาย)
- **ไม่มีแผนส่งต่องานประจำปี (Rotation Handover):** resident R2/R3 หมุนเวียนทุกปี ไม่มีขั้นตอนสอนงาน/onboarding รุ่นใหม่ ให้เข้าใจระบบและ escalation matrix ก่อนเริ่มเวร

### 3.6 ความกำกวมของ SLA

24 ชม. (Yellow) / 48 ชม. (Red) ไม่ระบุว่านับเป็นชั่วโมงปฏิทินหรือเวลาทำการ และไม่ครอบคลุมกรณีวันหยุดนักขัตฤกษ์/เสาร์-อาทิตย์ ซึ่งอาจทำให้เคสที่ยื่นวันศุกร์บ่ายโดนแจ้ง Red Alert ทั้งที่ยังไม่มีใครเห็นเพราะเป็นวันหยุด นอกจากนี้ไม่มี fast-track/emergency path สำหรับเคสที่ต้องตอบสนองเร็วกว่า 24 ชั่วโมง (เช่น กลุ่ม 3 ที่มีภาวะฉุกเฉินต้องการเตียงด่วน)

### 3.7 ไม่มีการตรวจสอบผู้ป่วยซ้ำ/ยืนยันตัวตน (Duplicate & Identity Matching)

ไม่มีขั้นตอนตรวจสอบว่าแพทย์ต้นทางเดียวกัน หรือแพทย์คนละแห่งส่งข้อมูลผู้ป่วยรายเดียวกันซ้ำ (เช่น ส่งทั้งกลุ่ม 1 และกลุ่ม 3 พร้อมกัน) และไม่มีการ match กับ HN เดิมของศิริราชถ้าผู้ป่วยเคยมีประวัติ อาจทำให้เกิดการนัดซ้ำซ้อนหรือ fellow เห็นเคสเดิมสองครั้ง

### 3.8 ไม่มีตัวชี้วัดผลลัพธ์ (KPI / Success Metrics)

เป้าหมายหลักของโครงการ (ลดภาวะ burnout, ปกป้องเวลาเรียนของ resident, ลดภาระธุรการ) ไม่มีตัวเลขวัดผลที่ชัดเจน เช่น:
- จำนวนครั้ง/สัปดาห์ที่ resident ถูกรบกวนนอกช่วง 10:00 น.
- turnaround time เฉลี่ยต่อกลุ่ม (1–4) เทียบก่อน-หลังใช้ระบบ
- อัตราเคสที่ incomplete/ต้องขอเอกสารเพิ่ม แยกตามกลุ่มโรค (leukemia/lymphoma/MM/allo-SCT)
- จำนวนชั่วโมงธุรการที่ลดลงของแพทย์ต้นทาง/resident (เทียบก่อน-หลัง)

### 3.9 ไม่มีแผน Testing / Pilot / Training / Timeline / งบประมาณ

ต่างจาก SRS.md เดิมที่มี Implementation Plan 5 phase และ Acceptance Criteria ครบ เอกสารนี้ยังขาดส่วนนี้ทั้งหมด — ไม่มีแผนอบรม resident/fellow/แพทย์แอดมินกลางก่อนใช้งานจริง ไม่มีเกณฑ์ว่าระบบพร้อม pilot เมื่อใด ไม่มีกรอบเวลาดำเนินโครงการ (timeline) และไม่มีประมาณการทรัพยากร/งบประมาณ (คน, เวลาโปรแกรมเมอร์, ค่าใช้จ่าย LINE OA)

### 3.10 ไม่มีแผนเมื่อระบบล่ม (Fallback/Business Continuity)

ไม่มีขั้นตอนสำรองเมื่อ Google Form/Apps Script/LINE Notify ใช้งานไม่ได้ชั่วคราว (เช่น ระบบล่ม, Google Workspace ปรับปรุง) — ต้องมีช่องทางธุรการสำรอง (เช่น เบอร์โทร/แฟกซ์ฉุกเฉิน) ระหว่างที่ระบบ digital ใช้ไม่ได้

## 4. ช่องว่างเฉพาะแต่ละกลุ่ม (Per-Group Gaps)

### กลุ่มที่ 1: Stem Cell Transplantation

- **Race condition การจองคิว:** ไม่มีการล็อกลำดับเมื่อผู้ส่ง refer 2 รายกดจองคิว fellow คนเดียวกัน ช่วงเวลาเดียวกันพร้อมกัน (ใครได้คิวที่เหลือ 1 ที่สุดท้าย)
- **การลา/ขาดของ fellow:** ไม่มีขั้นตอนเมื่อ fellow ที่ถูกระบุชื่อในใบ refer ลาป่วย/ลากะทันหันในวันนัด ผู้ป่วยที่เดินทางมาแล้วจะได้รับการดูแลอย่างไร
- **การยกเลิก/เลื่อนนัดจากฝั่งผู้ป่วย:** ไม่มี flow สำหรับผู้ป่วยที่ต้องการเลื่อนนัดหลังจองคิวไปแล้ว
- **ไม่มี priority lane:** เคสด่วนทางคลินิก (เช่น cytopenia รุนแรง) ต้องรอคิวเหมือนเคส routine ทั้งที่ fellow เต็มแล้ว

### กลุ่มที่ 2: ขอความเห็นสูตรยาเคมีบำบัด

- **ไม่มี path เมื่อไม่มี template ตรงกับเคส:** ถ้าไม่มีสูตรยามาตรฐานในคลังข้อมูลที่ตรงกับ diagnosis/stage ของเคส resident ต้องทำอย่างไร (พิมพ์เอง? ส่งต่อ Attending โดยตรง?) เอกสารไม่ได้ระบุ fallback
- **ไม่มี path เมื่อ Attending ไม่อนุมัติ/ขอแก้ไข:** ระบุแค่ "กดอนุมัติ" ไม่มีขั้นตอน reject/ขอแก้ไขก่อนส่งกลับแพทย์ต้นทาง
- **ไม่มี SLA เฉพาะกลุ่ม:** ใช้ 48 ชม. เดียวกับภาพรวม แต่ไม่ระบุว่านับจากตอนส่งฟอร์ม หรือจาก resident เปิดอ่าน หรือจาก Attending อนุมัติ

### กลุ่มที่ 3: ขอ Admit ให้ยาเคมีบำบัด/ยากดภูมิ

- **Loop ยังไม่ปิดหลังประเมินความพร้อม:** เมื่อนัด resident ประเมินร่างกายที่ OPD700 แล้ว "ผ่าน" ไม่มีขั้นตอนต่อว่าใครจอง/ยืนยันเตียงจริง มีคิวรอเตียงหรือไม่ ผู้ป่วยจะทราบวัน admit เมื่อใด
- **ไม่มี fast-track ฉุกเฉิน:** เคสที่ต้องการเตียงด่วน (เช่น neutropenic fever, tumor lysis) ไม่มีช่องทางแยกจาก queue ปกติ 48 ชม.
- **ไม่ชัดว่า "ให้คำแนะนำกลับ" ครอบคลุมความรับผิดชอบทางกฎหมายอย่างไร** หากแพทย์ต้นทางรักษาต่อเองแล้วเกิดภาวะแทรกซ้อน ใครเป็นผู้รับผิดชอบคำแนะนำที่ให้ไป (ควรมี documentation ของคำแนะนำใน record)

### กลุ่มที่ 4: Refer OPD ด้วยเหตุผลอื่น

- **ไม่มีทางเลือกสำหรับผู้ป่วยที่ไม่มีสมาร์ทโฟน/ไม่ใช้ LINE:** ระบบพึ่ง QR code/Siriraj Connect ทั้งหมด ผู้สูงอายุหรือผู้ป่วยที่ไม่ถนัดเทคโนโลยีอาจติดขัด ต้องมีช่องทางโทรศัพท์/เจ้าหน้าที่ช่วยจองแทน
- **ไม่มีการตรวจสอบว่าเคสที่ "fully automated" นี้ถูกจัดกลุ่มถูกต้องจริง:** เพราะไม่มีใครตรวจสอบเลย ถ้าแพทย์ต้นทางเลือกกลุ่มผิด (เช่น จริง ๆ ควรอยู่กลุ่ม 1-3) เคสจะหลุดออกจากระบบติดตามไปเลยโดยไม่มีใครรู้

## 5. ข้อเสนอขั้นตอนถัดไป (ลำดับความสำคัญ)

8. **เพิ่ม KPI, แผน pilot/training, timeline และประมาณการทรัพยากร** ก่อนเสนอขออนุมัติ/ทดลองใช้จริง
9. **เพิ่มแผนสำรองเมื่อระบบล่ม (fallback/BCP)**

## 6. คำตอบและข้อเสนอแนะเชิงออกแบบ (Design Decisions — อัปเดต 2026-07-29 รอบ 3)

ส่วนนี้ตอบข้อ 1–4 ที่เจ้าของโครงการเสนอมา พร้อมข้อเสนอแนะเพิ่มเติม

### 6.1 PDPA Consent — แนวทางที่เสนอมาใช้ได้ แต่ต้องปรับถ้อยคำเรื่อง "ไม่รับผิดชอบ"

แนวทาง **ถูกทิศทาง**: ให้แพทย์ต้นทางเป็นผู้แจ้งและรับทราบจากผู้ป่วยก่อนส่งข้อมูล เพราะแพทย์ต้นทางเป็นผู้พบผู้ป่วยจริง ส่วนศิริราชไม่มีทางขอความยินยอมจากผู้ป่วยได้เองในขั้นตอนนี้ — ตรงกับหลักการ PDPA-002 ที่ SRS.md วางไว้อยู่แล้ว

**ข้อควรระวัง 1 จุด:** คำว่า "ไม่รับผิดชอบ" ใช้แบบเหมาเข่งไม่ได้ตามกฎหมาย PDPA — การให้ผู้ป่วยเซ็นรับทราบความเสี่ยงช่วยเรื่อง *lawful basis ของการส่งข้อมูล* เท่านั้น แต่ศิริราชในฐานะผู้ควบคุมข้อมูลเมื่อรับข้อมูลมาแล้ว ยังมีหน้าที่ตาม PDPA-003 ถึง PDPA-007 ใน SRS.md อยู่ดี (data minimization, access control, retention, breach response) ไม่สามารถเขียนสละสิทธิ์ผู้ป่วยล่วงหน้าได้ทั้งหมด — ควรใช้คำว่า "รับทราบความเสี่ยงและยินยอมให้ส่งข้อมูล" แทน "ไม่รับผิดชอบ"

**ข้อเสนอ 2 ชั้นเอกสาร:**

1. **Checkbox บังคับใน Google Form** (สำหรับแพทย์ต้นทางผู้กรอก):
   > "ข้าพเจ้าในฐานะแพทย์ผู้ส่งต่อ ขอรับรองว่าได้แจ้งผู้ป่วย/ผู้แทนโดยชอบธรรมให้ทราบแล้วว่า ข้อมูลการรักษาบางส่วนจะถูกส่งผ่านระบบ Google Form ไปยังศิริราชเพื่อวัตถุประสงค์การประเมินและนัดหมายส่งต่อการรักษา และมีหนังสือรับทราบเก็บไว้ที่ต้นทางแล้ว"

2. **แบบฟอร์มสิ่งพิมพ์ (PDF) ให้ รพ.ต้นทาง print ให้ผู้ป่วยเซ็น เก็บไว้ที่ต้นทาง** (ไม่ต้องส่งกลับมาศิริราชเพื่อลดข้อมูลซ้ำซ้อน) ร่างข้อความเบื้องต้น:

   > **หนังสือรับทราบการส่งข้อมูลเพื่อส่งต่อผู้ป่วยผ่านระบบอิเล็กทรอนิกส์**
   >
   > ข้าพเจ้า (ผู้ป่วย/ผู้แทนโดยชอบธรรม) ชื่อ .................................... ได้รับทราบจากแพทย์ผู้ดูแลว่า ข้อมูลประวัติการรักษาบางส่วน (เช่น การวินิจฉัยโรค ผลตรวจ และสรุปการรักษา) จะถูกบันทึกและส่งผ่านระบบ Google Form ไปยังคณะแพทยศาสตร์ศิริราชพยาบาล เพื่อวัตถุประสงค์ในการประเมินและนัดหมายส่งต่อการรักษาเท่านั้น
   >
   > ข้าพเจ้ารับทราบว่าระบบดังกล่าวเป็นบริการของผู้ให้บริการภายนอก (Google) ซึ่งมีความเสี่ยงด้านความปลอดภัยของข้อมูลตามเงื่อนไขการให้บริการของผู้ให้บริการ แม้หน่วยงานจะมีมาตรการจำกัดสิทธิ์การเข้าถึงแล้วก็ตาม
   >
   > ข้าพเจ้ายินยอมให้ส่งข้อมูลดังกล่าวเพื่อวัตถุประสงค์การรักษาต่อเนื่อง และทราบว่าสามารถสอบถามหรือถอนความยินยอมเพิ่มเติมได้ที่ [ช่องทางติดต่อของ รพ.ต้นทาง]
   >
   > ลงชื่อผู้ป่วย/ผู้แทน ..................... วันที่ ................. &nbsp;&nbsp;&nbsp; ลงชื่อแพทย์ผู้แจ้ง .....................................

   *(ควรให้ DPO/ฝ่ายกฎหมายของศิริราชตรวจถ้อยคำสุดท้ายก่อนใช้จริง โดยเฉพาะฐานกฎหมายที่อ้างอิง เช่น "เพื่อประโยชน์ทางการแพทย์"/"ประโยชน์สาธารณะด้านสาธารณสุข" ตาม PDPA มาตรา 26)*

### 6.2 Hosting: Cloudflare Pages หรือ Vercel

**ข้อเสนอ: ใช้ Cloudflare Pages** ด้วยเหตุผล:

| ปัจจัย | Cloudflare Pages | Vercel |
| --- | --- | --- |
| ความเข้ากันกับ Next.js App Router | ต้องใช้ `@cloudflare/next-on-pages` หรือ OpenNext adapter, มีข้อจำกัดกับบาง Node API | รองรับเต็มรูปแบบ zero-config (เจ้าของ framework) |
| Access control หน้า Dashboard | มี **Cloudflare Access** ในตัว (Zero Trust) กั้นด้วย SSO/อีเมลองค์กรได้ฟรี โดยไม่ต้องเขียนระบบ login เอง | ไม่มีในตัว ต้องต่อ NextAuth + Google OAuth เอง |
| ความสอดคล้องกับ stack เดิม | ทีมมีโปรเจกต์ hemato-elective.pages.dev บน Cloudflare Pages + Turso อยู่แล้ว — ใช้ operational knowledge เดิมได้ | เป็น stack ใหม่ที่ต้องเรียนรู้เพิ่ม |
| เรียก Google Sheets API | ต้องเลี่ยง `googleapis` SDK แบบเต็ม (หนักเกิน edge runtime) ใช้ REST call + JWT เซ็นเองแทน | เรียก `googleapis` SDK ได้ตรงบน Node.js runtime ไม่มีข้อจำกัด |

**สรุป:** แนะนำ **Cloudflare Pages** เพื่อความสอดคล้องกับ infra เดิม และได้ Cloudflare Access มากั้นหน้า `/dashboard` ให้เฉพาะบุคลากรฟรีทันที (ตรงกับ requirement PDPA-004 เรื่อง access control พอดี) แต่ต้องเขียนโค้ดเรียก Google Sheets API แบบ REST + JWT แทนการใช้ SDK เต็ม ถ้าทีมอยากได้ deploy ที่ friction น้อยที่สุดโดยไม่สนเรื่อง auth ในตัว ให้ใช้ Vercel แทนแล้วต่อ NextAuth เอง

ไม่ว่าจะเลือกแพลตฟอร์มไหน ต้องเก็บ Google service-account credentials ไว้ฝั่ง server (environment secret) เท่านั้น ห้าม expose ใน client code ตาม NFR-003 ที่มีอยู่แล้ว

### 6.3 หน้าเว็บหลักแบบ Single Entry + LINE-first — เห็นด้วย

ออกแบบตามนี้ได้เลย และช่วยแก้ gap ข้อ 4.4 (กลุ่ม 4 misclassification) ไปในตัว:

- **หน้า Landing เดียว** มีปุ่มใหญ่ 4 ปุ่มตรงกับ 4 กลุ่ม (ใช้ emoji เดิมจากเอกสาร: 📋 นัด Transplant / 📋 ขอ consult สูตรยา / 🏥 ขอ Admit เคมี / 🌐 Refer เหตุผลอื่น) แต่ละปุ่มลิงก์ไป Google Form ของกลุ่มนั้น
- เพิ่มปุ่มที่ 5 เสมอ: **"ไม่แน่ใจว่าเข้ากลุ่มไหน"** → ให้ติดต่อเจ้าหน้าที่โดยตรงแทนการเดา ลดความเสี่ยงเคสหลุดจากกลุ่ม 4 อัตโนมัติทั้งที่จริงควรเข้ากลุ่ม 1-3
- **LINE Official Account** เป็นทางเข้าคู่ขนาน: ตั้ง Rich Menu 5 ปุ่มเดียวกัน เปิดลิงก์ไปหน้าเดียวกัน เหมาะกับแพทย์ต้นทางที่ใช้มือถือเป็นหลัก ตามที่เสนอ

## 7. ข้อเสนอแนะสำหรับประเด็นที่เหลือ (ตามข้อ 5 — เพิ่มเติมให้ครบ)

### 7.1 นิยาม SLA ให้ชัดเจน

- นับเป็น **เวลาทำการ** (08:00–16:00 น. วันจันทร์-ศุกร์ ไม่รวมวันหยุดนักขัตฤกษ์) ไม่ใช่ชั่วโมงปฏิทิน เพื่อไม่ให้ตัวนับเดินระหว่างวันหยุด
- เพิ่ม **fast-track flag**: ให้แพทย์ต้นทางเลือก "ด่วนมาก/ฉุกเฉิน" ในฟอร์ม ถ้าเลือก ระบบส่ง LINE แจ้งทันทีถึงคุณหมอแอดมินกลางโดยไม่ต้องรอ batch 10:00 น. (ใช้กับกลุ่ม 1 และ 3 ที่มีโอกาสเป็นเคสฉุกเฉินทางคลินิก)

### 7.2 ตรวจสอบเคสซ้ำ/ยืนยันตัวตน (Duplicate & HN Matching)

- ให้ field HN ศิริราช (ถ้ามี) เป็นตัวช่วย match เบื้องต้น ถ้าไม่มี ใช้ ชื่อ-สกุล + วันเกิด/อายุ เทียบกับเคสที่ยื่นในช่วง 30 วันล่าสุดใน Google Sheet (เขียนเป็น Apps Script ตรวจแบบง่าย ไม่ต้อง auto-merge แค่ flag ให้เจ้าหน้าที่ตรวจสอบเอง)

### 7.3 KPI เริ่มต้นสำหรับช่วง Pilot

- Turnaround time เฉลี่ยต่อกลุ่ม (1–4)
- จำนวนครั้งที่ resident ถูกแจ้งเตือนนอกช่วง 10:00 น. (ควรเป็น 0 ถ้าระบบทำงานตามออกแบบ)
- อัตราเคส incomplete/ต้องขอเอกสารเพิ่มต่อเดือน
- จำนวน Yellow/Red Alert ต่อเดือน (ควรลดลงเรื่อย ๆ)
- สรุปเป็นรายงานเดือนละครั้งจาก Google Sheet pivot table

### 7.4 แผน Testing / Pilot / Timeline (ตัวอย่างคร่าว ๆ ให้ทีมปรับ)

1. **สัปดาห์ 1–2:** สร้าง Google Form/Sheet + หน้า web landing + เชื่อม LINE OA
2. **สัปดาห์ 3:** ทดสอบภายในทีม (ทุก role กดทดสอบเคสจำลองครบทั้ง 4 กลุ่ม)
3. **สัปดาห์ 4–7:** Pilot กับ รพ.เครือข่ายที่ส่ง refer บ่อย 1–2 แห่งก่อน เก็บ feedback หลังปิดเคสทุกครั้งด้วยฟอร์มสั้น ๆ
4. **หลังจากนั้น:** ขยายไปทุกโรงพยาบาลเครือข่าย พร้อมทบทวน KPI รอบแรก

### 7.5 แผนสำรองเมื่อระบบล่ม (BCP)

- แสดงเบอร์โทรศัพท์/ช่องทางติดต่อฉุกเฉินไว้บนหน้า web portal เสมอ (กรณี Google Form/LINE ใช้งานไม่ได้)
- ถ้า Apps Script/LINE Notify ล่มเกิน 1 วันทำการ ให้แจ้งเวียนทาง email/ประกาศในกลุ่มไลน์แพทย์เครือข่ายว่าใช้ช่องทางโทรศัพท์ชั่วคราว

## 8. ข้อสรุปรอบที่สอง (อาจารย์ตัดสิน 29 กรกฎาคม 2569)

| # | ประเด็น | มติ |
| --- | --- | --- |
| **ก** | เก็บข้อมูลบน Google Sheet | **ได้** โดยไม่ใส่ชื่อและ HN และให้มีการแจ้งข้อมูล + ช่องรับทราบก่อนกรอก เก็บไว้เป็นหลักฐานทางกฎหมาย — **ไม่ต้องขอคำยืนยันจากฝ่ายสารสนเทศ** เพราะเป็นการดำเนินการภายในหน่วยย่อยเอง |
| **ข** | นำเรียน DPO | **ยังไม่ต้อง** เพราะของเดิมก็ดำเนินการอยู่แล้ว หากมีระเบียบกำหนดในอนาคตค่อยยื่นเรื่อง |
| **ค** | LINE OA | **สร้างใหม่** ตามที่ทีมเสนอ |
| **ง** | ระยะเวลาเก็บข้อมูล | **แยก 3 ชุด** ตามที่ทีมเสนอ พร้อมเพิ่มชุดสถิติสรุป — ดู SRS §PDPA-005 |

### 8.1 ผลของมติข้อ ก และ ข ต่อการออกแบบ

เมื่อไม่มีการรับรองจากฝ่ายสารสนเทศและยังไม่ผ่าน DPO **ช่องรับทราบก่อนกรอกฟอร์มจึงกลายเป็นหลักฐานหลักเพียงอย่างเดียวของระบบ** ส่วนนี้ต้องทำให้รัดกุมเป็นพิเศษ:

- checkbox ต้องเป็น **required** ข้ามไม่ได้ และต้องบันทึก timestamp ที่ติ๊กลงในฐานข้อมูล (field `consent_acknowledged`)
- ข้อความต้องระบุให้ครบว่า เก็บอะไร ใครเข้าถึงได้ เก็บนานเท่าใด และติดต่อใครได้
- หน้า `/consent` สำหรับให้ผู้ป่วยลงนามยังคงต้องใช้ควบคู่ และเก็บต้นฉบับที่โรงพยาบาลต้นทาง
- ระบุในเอกสารให้ชัดว่าเป็น**เครื่องมือช่วยงานภายในหน่วยงาน ไม่ใช่ระบบเวชระเบียน**
- ทบทวนรายชื่อผู้เข้าถึง Google Sheet ทุก 3 เดือน และห้ามตั้งเป็น "anyone with link" เด็ดขาด

ทั้งนี้ควรทบทวนมติข้อ ก และ ข อีกครั้งเมื่อระบบขยายออกนอกหน่วยงาน หรือเมื่อปริมาณข้อมูลสะสมมากขึ้น

### 8.2 LINE OA ใหม่ — สิ่งที่ต้องทำ

- สร้างบัญชีใหม่ ตั้ง Rich Menu ให้ตรงกับ 4 กลุ่มบนหน้าเว็บ
- บัญชีเดิมเปิดไว้ช่วงเปลี่ยนผ่าน ตั้งข้อความอัตโนมัติชี้มาบัญชีใหม่
- กำหนดผู้ดูแล credential และ token ให้ชัดเจน (Technical Admin ตาม SRS §22)
- เมื่อเลิกใช้บัญชีเดิม ควรพิจารณาลบประวัติสนทนาที่มีชื่อและ HN ของผู้ป่วย

### 8.3 ที่เก็บข้อมูลของแต่ละชุด

อาจารย์ถามว่าควรเก็บใน Google หรือ database ทีมเสนอให้**แยกตามชุดข้อมูล** เพราะความต้องการต่างกัน

| ชุด | ที่เก็บที่แนะนำ | เหตุผล |
| --- | --- | --- |
| **1. เคสเต็ม** (2–3 ปี) | Google Sheet ในระยะ pilot → ย้ายเข้า **Cloudflare D1** เมื่อขยายหรือข้อมูลเกิน ~3,000 แถว | ต้องลบตามกำหนดเวลา ซึ่ง SQL ทำได้ในคำสั่งเดียวและตรวจสอบได้ ส่วน Sheet ต้องเขียน script เองและพลาดง่าย |
| **2. คลังคำตอบ** (ถาวร) | **Google Sheet** ไม่ต้องย้าย | ไม่มีข้อมูลส่วนบุคคล ความเสี่ยงต่ำ และแพทย์ควรแก้ไข/เพิ่มสูตรได้เองโดยไม่ต้องพึ่งโปรแกรมเมอร์ — Sheet เหมาะกว่า database ในกรณีนี้ |
| **3. สถิติสรุป** (ถาวร) | **Google Sheet** | ตัวเลขล้วน ทำ pivot table และกราฟได้ทันที |

**เหตุผลที่แนะนำ Cloudflare D1 สำหรับชุดที่ 1** (เมื่อถึงเวลาย้าย):

- เป็นบริการในตัวของ Cloudflare ที่เลือกใช้ deploy อยู่แล้ว ไม่ต้องเพิ่มบริการหรือ credential ใหม่
- เข้าถึงได้เฉพาะผ่านแอปที่มี Cloudflare Access กั้น — ไม่มีทางเกิดอุบัติเหตุ "แชร์ลิงก์หลุด" แบบ Google Sheet ซึ่งเป็นความเสี่ยงอันดับหนึ่ง
- ลบข้อมูลตามกำหนดได้อัตโนมัติและตรวจสอบได้
- ยังเร็วแม้ข้อมูลจะสะสมมาก

ทางเลือกที่เทียบเท่าคือ **Turso** ซึ่งทีมมีประสบการณ์อยู่แล้วจากโปรเจกต์อื่น ทั้งสองตัวเป็น SQLite เหมือนกัน ย้ายข้ามกันภายหลังได้ไม่ยาก จึงไม่ถือเป็นการผูกมัด

**ข้อสรุปเชิงปฏิบัติ:** เริ่มด้วย Google Sheet ทั้งหมดในระยะ pilot ได้เลย ไม่ต้องรอ database — แต่ควรออกแบบโครงสร้างข้อมูลตั้งแต่ต้นให้ย้ายได้ง่าย (หนึ่งแถวต่อหนึ่งเคส ชื่อคอลัมน์ตรงกับ field ในโค้ด ไม่ใช้สูตรข้ามชีต)
