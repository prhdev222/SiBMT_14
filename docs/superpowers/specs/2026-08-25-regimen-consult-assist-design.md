## 2. ปัญหา

การขอความเห็นสูตรยาเคมีบำบัดจากแพทย์ต้นทางมีปัญหาสามชั้นที่ซ้อนกัน

1. **ข้อมูลมาไม่ครบ** — [Section 5](../../FORMS_AND_SHEETS.md) ของฟอร์มปัจจุบันเก็บ 7 ข้อ
   ออกแบบมาเพื่อคัดแยกเคส ไม่ใช่เพื่อเลือกสูตรยา ทำให้ต้องถามกลับหลายรอบ
2. **คำตอบไม่ได้ขึ้นกับ guideline อย่างเดียว** — ขึ้นกับสิทธิการรักษาของผู้ป่วยและ
   บัญชียาของโรงพยาบาลด้วย ซึ่งเป็นความรู้ท้องถิ่นที่ไม่มีอยู่ในแหล่งอ้างอิงสากลใด ๆ
3. **guideline ปรับอยู่เรื่อย ๆ** และการตามอ่านทุกโรคเป็นภาระที่หนักเกินกว่าที่คนคนเดียวจะทำได้

**ข้อสังเกตที่กำหนดทั้งดีไซน์:** ปัญหาข้อ 2 ไม่ใช่ปัญหาที่ต้องใช้ AI แก้ มันคือปัญหา
**การจับคู่ภายใต้ข้อจำกัด (constraint matching)** ซึ่งมีคำตอบตายตัว ตรวจสอบได้ และหลอนไม่ได้

## 3. คำถามวิจัย

> เครื่องมือที่ (ก) บังคับความครบถ้วนของข้อมูลตั้งแต่ต้นทาง และ (ข) จับคู่สูตรยาจาก
> guideline สมาคมโลหิตวิทยา เข้ากับสิทธิการรักษาและบัญชียาศิริราช
> จะลดจำนวนรอบการถาม-ตอบ เพิ่มความถูกต้องของตัวเลือกที่เสนอ และได้รับการยอมรับจาก
> resident และ attending หรือไม่

**คำถามรอง** — ข้อมูลข้อใดบ้างที่เปลี่ยนคำตอบของ attending จริง (ชุดข้อมูลขั้นต่ำ)
และตัวเลือกการรักษาต่างกันเพียงใดเมื่อสิทธิการรักษาต่างกัน

## 4. สิ่งที่จะสร้าง

องค์ประกอบสี่ชิ้น เรียงจากความเสี่ยงต่ำไปสูง **แยกกันได้อิสระ** — ถ้าชิ้นท้าย ๆ
ไม่สำเร็จ ยังส่งเล่มด้วยชิ้นต้น ๆ ได้

| # | ชิ้นส่วน | กลไก | ความเสี่ยงคลินิก |
| --- | --- | --- | --- |
| ① | ฟอร์มกลุ่ม 2 ใหม่ + ตรวจความครบถ้วน + วนถามกลับ | กฎตายตัว + LLM อ่าน free text | ไม่มี |
| ② | จับคู่สูตรยาภายใต้ข้อจำกัด | rules engine ล้วน | ต่ำ |
| ③ | แจ้งเตือนเมื่อ guideline ของโรคนั้นถูกปรับ | ข้อมูลมีเวอร์ชัน + คนเฝ้า | ต่ำ |
| ④ | สรุปเคสให้ attending อ่าน | LLM summarization | ปานกลาง |

## 5. ฐานความรู้

หัวใจของระบบ ทุกระเบียนต้องมี `effective_from`, `effective_to`, `source`, `reviewed_by`, `reviewed_at`

### 5.1 ชั้นข้อมูล

| ชั้น | เนื้อหา | เจ้าของ | รอบทบทวน |
| --- | --- | --- | --- |
| `regimen` | สูตรยา — ชื่อ ส่วนประกอบ จำนวนรอบ ข้อความคำต่อคำจาก guideline | แพทย์แอดมินกลาง | ทุก 6 เดือน หรือเมื่อ guideline ปรับ |
| `indication` | เงื่อนไขที่สูตรนั้นใช้ได้ — โรค, subtype, stage/risk, line of therapy, intent, ข้อจำกัดอายุ/PS/การทำงานของอวัยวะ | แพทย์แอดมินกลาง | เท่ากับ `regimen` |
| `coverage` | สิทธิแต่ละประเภทเบิกยาแต่ละตัวได้หรือไม่ + เงื่อนไข จ(2) | ต้องระบุชื่อ (§12) | ทุก 3 เดือน |
| `formulary` | ยาที่มีในบัญชีโรงพยาบาลศิริราช | ต้องระบุชื่อ (§12) | ทุก 3 เดือน |
| `self_pay` | ยาที่ไม่อยู่ในสิทธิ + ราคาโดยประมาณ + วันที่อ้างอิงราคา | ต้องระบุชื่อ (§12) | ทุก 3 เดือน |
| `guideline_version` | ฉบับ วันที่ประกาศ และสรุปสิ่งที่เปลี่ยน | ต้องระบุชื่อ (§12) | เฝ้าดูต่อเนื่อง |

### 5.2 กติกาที่ห้ามละเมิด

- **ข้อความสูตรยาต้องแสดงคำต่อคำจากต้นฉบับ** พร้อมลิงก์กลับไปยังแหล่งที่มา
  ห้ามให้โมเดลเรียบเรียงใหม่ในส่วนนี้
- **ทุกหน้าจอที่แสดงสูตรยาต้องมีบรรทัด "ข้อมูล ณ วันที่ …"**
- **ข้อมูลที่หมดอายุ (`effective_to` ผ่านไปแล้ว) ต้องไม่ถูกเสนอ** และต้องขึ้นคำเตือนแทน
- ฐานความรู้ล้าสมัยอันตรายกว่าไม่มีระบบ เพราะดูน่าเชื่อถือ — §11 กำหนดมาตรการ

## 6. Rules engine และขอบเขตของ LLM

```
สูตรที่เสนอ = indication(โรค, subtype, stage, line, intent, PS, การทำงานของอวัยวะ)
             ∩ coverage(สิทธิของผู้ป่วย)
             ∩ formulary(ศิริราช)

แยกแสดงต่างหาก:
  • สูตรที่ตรง indication แต่สิทธิไม่ครอบคลุม → ชั้น "ต้องชำระเอง" พร้อมราคา
  • สูตรที่ตรง indication แต่ศิริราชไม่มียา   → แสดงพร้อมเหตุผล
  • ไม่มีสูตรใดตรงเลย                        → ตอบว่า "ไม่มี" แล้วส่งต่อ attending
```

**ทุกผลลัพธ์ต้องอธิบายได้ว่าทำไมถูกเสนอหรือทำไมถูกตัด** — แสดงเป็นรายการเงื่อนไขที่ผ่าน/ไม่ผ่าน

### LLM ทำได้เฉพาะสองงานนี้

| งาน | รับเข้า | ส่งออก | วัดด้วย |
| --- | --- | --- | --- |
| Extraction (①) | free text จากฟอร์ม | ฟิลด์นี้มีข้อมูลแล้วหรือยัง | precision/recall รายฟิลด์ |
| Summarization (④) | ฟิลด์ที่กรอกครบแล้ว | ย่อหน้าสรุปเคส | fidelity / omission rate |

**LLM ไม่แตะการเลือกสูตร ไม่แตะขนาดยา ไม่แตะการตัดสินใจใด ๆ**

**ผู้ให้บริการ:** Cloudflare Workers AI — ระบบ deploy บน Cloudflare อยู่แล้วและมี binding พร้อม
([DEPLOYMENT.md](../../DEPLOYMENT.md)) จึงไม่เพิ่ม data processor รายใหม่ ไม่ต้องกลับไปขอมติใหม่

## 7. ฟอร์มกลุ่มที่ 2 ที่ออกแบบใหม่

### 7.1 ที่เพิ่มใน Section 2 (ทุกกลุ่ม)

| ฟิลด์ | ประเภท | บังคับ | เหตุผล |
| --- | --- | --- | --- |
| `coverage_scheme` | MC: บัตรทอง / ประกันสังคม / ข้าราชการ / ประกันเอกชน / ชำระเอง | ✅ | ตัวแปรที่กำหนดคำตอบมากที่สุด **ปัจจุบันไม่ถามเลย** |

> นี่คือการแก้ส่วนที่**ทุกกลุ่มใช้ร่วมกัน** ไม่ใช่เฉพาะกลุ่ม 2 — เป็นการเปลี่ยนแปลง
> นอกขอบเขตที่ตั้งใจ เพราะกลุ่ม 1 และ 3 ได้ประโยชน์ด้วยและการแยกถามเฉพาะกลุ่ม 2
> จะทำให้ฟอร์มไม่สม่ำเสมอ ต้องแจ้งอาจารย์ก่อนแก้

### 7.2 Section 5 ใหม่

คงของเดิม 7 ข้อ แล้วเพิ่ม/ปรับ

| ฟิลด์ | ประเภท | บังคับ | หมายเหตุ |
| --- | --- | --- | --- |
| `performance_status` | MC: ECOG 0–4 | ✅ | **ปัจจุบันไม่มีในกลุ่ม 2 ทั้งที่กลุ่ม 3 มี** |
| `line_of_therapy` | MC: 1st line / relapsed / refractory / maintenance | ✅ | ปัจจุบันต้องเดาจาก free text |
| `treatment_intent` | MC: curative / palliative / ยังไม่ตัดสินใจ | ✅ | เปลี่ยนคำตอบทั้งหมด |
| `comorbidity` | Paragraph | ✅ | เดิมเป็น optional — สลับกับกลุ่ม 3 ที่บังคับ |
| `renal_function` | ตัวเลข Cr หรือ CrCl + วันที่ | ✅ | ตัดสินว่าให้ยาได้ไหม/ลดขนาดไหม |
| `hepatic_function` | ตัวเลข bilirubin, AST/ALT + วันที่ | ✅ | เช่นเดียวกัน |
| `viral_status` | Checkbox: HBsAg / anti-HBc / anti-HCV / anti-HIV + ผล | ✅ | HBV reactivation ก่อน rituximab/chemo |
| `pathology_confirmed` | MC: ยืนยันแล้ว / รอผล / ไม่ได้ทำ | ✅ | เผื่อต้อง review block slide |
| `local_admin_capable` | MC: ให้เองได้ / ให้เองไม่ได้ / ไม่แน่ใจ | ✅ | ถ้าให้เองไม่ได้ คำตอบเปลี่ยนเป็น "ส่งตัวมา" = กลุ่ม 3 |
| `j2_registered` | MC: ขึ้นทะเบียนแล้ว / ยังไม่ได้ / ไม่เกี่ยวข้อง | ❌ | เฉพาะโรคที่มียาบัญชี จ(2) |
| ฟิลด์เฉพาะโรค | แยก branch ตามโรคที่เลือก | ✅ | เช่น lymphoma → histology subtype, IPI, CD20 · AML → cytogenetics, FLT3/NPM1 · แทนที่จะยัดรวมในช่อง `stage` |

### 7.3 กันภาระการกรอก

เพิ่มฟิลด์ = เสี่ยงเลิกกรอกกลางคัน กันสามชั้น

1. **branch ตามโรค** — เห็นเฉพาะคำถามของโรคตัวเอง
2. **เปลี่ยน paragraph เป็น dropdown/checkbox ให้มากที่สุด** — เร็วขึ้นและเครื่องอ่านได้
3. **วัดผล** — completion rate, เวลาที่ใช้กรอก, จุดที่ออกกลางคัน เป็น endpoint ที่เก็บได้ทุกเคส

## 8. Flow และนาฬิกา

```
แพทย์ต้นทางกรอกฟอร์ม
   │
   ├─► ① ตรวจความครบถ้วนทันทีที่กดส่ง (ไม่รอรอบ 10:00)
   │      ไม่ครบ → LINE + ลิงก์เติมข้อมูลผูกกับรหัสอ้างอิง → วนกลับ
   │      ครบ    → ต่อ
   ▼
② rules engine จับคู่สูตร → เสนอ + เหตุผลที่ตัดออก + ชั้นชำระเอง
   ▼
③ ถ้า guideline โรคนี้เพิ่งปรับ → แสดงว่าเปลี่ยนอะไร
   ▼
④ สรุปเคส แสดง**คู่กับข้อมูลดิบเสมอ** ทุกประโยคชี้กลับฟิลด์ต้นทางได้
   ▼
Resident อ่าน เลือก ร่างคำตอบ
   ▼
Attending อนุมัติ / แก้ / เขียนใหม่          ← ผู้รับผิดชอบคำตอบ
   ▼
บันทึกลง advice_record (ใช้กลไกที่มีอยู่แล้ว) → ส่งกลับแพทย์ต้นทาง
```

**ขั้นสุดท้ายห้ามใช้ Google Form ใบใหม่** — ต้องเขียนลง `advice_record` ของเคสเดิม
ผ่านหน้า dashboard ที่สร้างไว้แล้ว (commit `1df0e14`) มิฉะนั้นจะเสีย audit trail
ตาม PDPA-005 และเสียข้อมูลเวลาที่ใช้วิจัย

### นาฬิกาสองเรือน

| นาฬิกา | เริ่มนับ | ใช้ทำอะไร |
| --- | --- | --- |
| ผู้ป่วย | ตั้งแต่ส่งฟอร์มครั้งแรก | วัดประสบการณ์จริง — อาจยาวขึ้นเพราะ loop ถามกลับ |
| ทีมศิริราช | เมื่อข้อมูลครบ | SLA 48 ชม. ทำการ ตามมติเดิม |

รายงานทั้งสองเรือนเสมอ พร้อมคำอธิบายว่าทำไมต่างกัน

## 9. แผนประเมิน

**ข้อจำกัดที่กำหนดดีไซน์ทั้งหมด:** กลุ่ม 2 มี 5–15 เคส/เดือน ทุกโรครวมกัน
เมื่อ scope เหลือโรคเดียว ประมาณการเคสจริงที่เก็บได้ตลอดโครงการคือ **~18 เคส**
ซึ่งไม่พอสำหรับการทดสอบสถิติ จึงย้าย primary endpoint ออกจาก "เคสจริง"

| ลำดับ | Endpoint | n | วิธี |
| --- | --- | --- | --- |
| **หลัก** | ความถูกต้องของ rules engine | **ครบทุกคู่** (subtype × line × intent × สิทธิ 5 ประเภท) — ดู §9.0 | ทดสอบครบถ้วน ไม่ต้องสุ่ม ไม่ต้องมี CI — เป็นระบบนิรนัย |
| **หลัก** | Retrieval accuracy บน vignette — precision@k, recall@k, MRR | **120–150 vignette** | เทียบกับ keyword search เป็น baseline |
| **หลัก** | Extraction accuracy (①) รายฟิลด์ | vignette ชุดเดียวกัน | precision/recall ต่อฟิลด์ |
| รอง | การยอมรับผู้ใช้ — SUS + UTAUT | 10–20 คน | n เป็นคน ไม่ใช่เคส จึงพอ |
| รอง | Fidelity ของสรุป (④) | vignette | อาจารย์ตรวจว่าเพิ่มหรือตกอะไร |
| รอง | Automation bias | 10–20 คน | ใส่คำแนะนำผิดโดยตั้งใจ วัดอัตราการจับได้ |
| เสริม | ใช้งานจริง — จำนวนรอบถาม-ตอบ, % ตอบได้เลย, อัตรา override, completion rate | ~18 เคส | **รายงานเชิงพรรณนา ไม่ทดสอบสถิติ** |
| วิเคราะห์ | ตัวเลือกต่างกันแค่ไหนเมื่อสิทธิต่างกัน | คำนวณล้วน | ผลเชิงระบบสุขภาพ ไม่ต้องใช้ผู้ป่วย |
| วิเคราะห์ | ข้อมูลข้อไหนเปลี่ยนคำตอบ attending จริง | ทุกเคส + vignette | ได้ชุดข้อมูลขั้นต่ำที่โรงพยาบาลอื่นใช้ต่อได้ |

### 9.0 ขนาดของพื้นที่การตัดสินใจ

สำหรับโรคเดียว พื้นที่ = subtype × line of therapy × intent × สิทธิ 5 ประเภท
โดยประมาณคือหลักร้อยถึงหลักพันชุด ซึ่ง**รันด้วยเครื่องได้ทั้งหมด**

แพทย์แอดมินกลางไม่ต้องตรวจทุกชุดด้วยตา — ให้ตรวจแบบ **stratified** คือ
สุ่มตรวจอย่างน้อย 3 ชุดต่อทุกค่าของทุกมิติ บวกกับ**ทุกชุดที่ระบบตอบว่า "ไม่มีสูตรที่ตรง"**
(เพราะเป็นกรณีที่ผิดพลาดแล้วเสียหายที่สุด) หากจำนวนชุดเกิน 2,000
ให้ทบทวนว่านิยาม `indication` ละเอียดเกินจำเป็นหรือไม่

### 9.1 Vignette — สร้างพร้อมกับ template

ทุกครั้งที่อาจารย์เรียบเรียง `regimen` + `indication` 1 รายการ ให้เขียน
**เคสจำลอง 3–5 เคสที่ควรค้นเจอสูตรนั้น** ต่อท้ายในเอกสารเดียวกัน

- 30 สูตร × 4 เคส = **120 vignette**
- ได้ ground truth ฟรี ไม่ต้องติดฉลากทีหลัง
- การันตีว่า test set ครอบคลุมตรงกับฐานความรู้
- ขอเวลาอาจารย์รอบเดียว ไม่ใช่สองรอบ
- ผลพลอยได้: การเขียนเคสที่ "ควรเจอสูตรนี้" บังคับให้นิยาม indication ชัดขึ้น

**ต้องรวมเคสก้ำกึ่งที่จงใจให้ยาก** และเคสที่ควรได้คำตอบว่า "ไม่มีสูตรที่ตรง"

### 9.2 Shadow mode

รันองค์ประกอบ ①②④ เงียบ ๆ เก็บผลลง log ไม่แสดงให้ผู้ใช้เห็น **4–6 สัปดาห์**
ก่อนเปิดใช้จริง — ปลอดภัย และได้ข้อมูลก่อน-หลังของตัวเครื่องมือเอง

### 9.3 baseline ที่ไม่มี

**ไม่มีข้อมูลย้อนหลังของการ refer ก่อนมีระบบ** จึงเปรียบเทียบ "ก่อน/หลังมีระบบ refer" ไม่ได้ตลอดไป
ดีไซน์นี้จึงใช้ **ระบบที่รันอยู่ตอนนี้โดยยังไม่เปิดเครื่องมือ เป็น control period**
และตัวแทรกแซงที่ถูกประเมินคือเครื่องมือช่วยตอบ ไม่ใช่ระบบ refer

เคสที่แพทย์ต้นทางยังโทรหรือ LINE ตรงหา resident โดยไม่ผ่านระบบ ให้นับไว้เป็น
usual care ที่รันคู่ขนาน

## 10. ธรรมาภิบาล

ไม่ใช่ภาคผนวก — **เป็นเส้นทางวิกฤต** เพราะทั้งสามองค์ประกอบพังทันทีถ้าฐานความรู้ล้าสมัย
[PROPOSAL_REVIEW §3.5](../../PROPOSAL_REVIEW.md) ระบุว่ายังไม่มีผู้ดูแล Template Library
และไม่มีรอบทบทวน — ต้องปิดก่อนเริ่ม

| บทบาท | หน้าที่ | สถานะ |
| --- | --- | --- |
| เจ้าของฐานความรู้สูตรยา | อนุมัติ `regimen` / `indication` ทุกรายการ | แพทย์แอดมินกลาง (ยังไม่มีผู้สำรอง) |
| ผู้ดูแลข้อมูลสิทธิและบัญชียา | ทบทวน `coverage` / `formulary` / `self_pay` ทุก 3 เดือน | **ยังไม่มีผู้รับ** |
| ผู้เฝ้าดู guideline | ติดตามประกาศสมาคมฯ บันทึกลง `guideline_version` | **ยังไม่มีผู้รับ** |
| ผู้ส่งต่องานประจำปี | onboard resident รุ่นใหม่ | **ยังไม่มีผู้รับ** |

**เกณฑ์หยุด:** ถ้าไม่มีผู้ดูแลข้อมูลสิทธิและบัญชียาที่มีชื่อจริง
**ห้ามเปิดใช้องค์ประกอบ ② กับผู้ใช้จริง**

การพัฒนาและการตรวจสอบ ② บน vignette และการทดสอบ rules engine **ยังทำต่อได้ตามปกติ**
เพราะไม่ต้องแตะผู้ป่วยหรือผู้ใช้ — ผลหลักของเล่ม (§9) จึงยังได้ครบ
สิ่งที่หายไปคือข้อมูลการใช้งานจริงของ ② ซึ่งเป็น endpoint เสริม ไม่ใช่ endpoint หลัก

## 14. เกณฑ์ความสำเร็จ

**ขั้นต่ำที่ทำให้ส่งเล่มได้**
1. rules engine ผ่านการทดสอบครบทุกคู่ โดยแพทย์แอดมินกลางรับรอง
2. วัด retrieval + extraction บน vignette ≥120 เคส เทียบกับ baseline
3. ฟอร์มใหม่ใช้งานจริงและมีข้อมูล completion rate
4. มีบทวิเคราะห์ NASSS ว่าทำไมยังขยายออกนอกศิริราชไม่ได้

**ที่ทำให้เล่มแข็ง**
5. SUS/UTAUT จากผู้ใช้จริง ≥10 คน
6. field-yield analysis ได้ชุดข้อมูลขั้นต่ำ
7. ตัวเลขความต่างของตัวเลือกการรักษาตามสิทธิ
8. automation bias test

**ที่ถือว่าล้มเหลว**
- ฐานความรู้ไม่มีเจ้าของ → ระบบตายภายในหนึ่งปีหลังส่งเล่ม
- แพทย์ต้นทางเลิกใช้ฟอร์มเพราะยาวเกิน → วัดจาก completion rate ที่ลดลง
- LLM ถูกใช้ในการเลือกสูตร ไม่ว่าด้วยเหตุผลใด
