## 1. Hemato Bot คืออะไร

วิดเจ็ตแชทลอยมุมขวาล่างของหน้าเว็บสาธารณะทุกหน้า (`src/components/hemato-bot/HematoBotWidget.tsx`
ฝังไว้ที่ `src/app/layout.tsx`) ให้แพทย์ต้นทางถามสถานะเคส อ่านคำตอบ ค้นสูตรยา
และดูเกณฑ์ปลูกถ่ายได้เองโดยไม่ต้องเปิดอีเมลหรือรอ resident ตอบในกลุ่ม LINE

**ซ่อนอัตโนมัติ** บนเส้นทางที่ขึ้นต้นด้วย `/dashboard`, `/login`, `/answer`
(`HIDDEN_PATH_PREFIXES` ใน `HematoBotWidget.tsx`) — เพราะหน้าพวกนี้เป็นของ
เจ้าหน้าที่ภายในหรือมีคำตอบเคสเปิดอยู่แล้ว ไม่ต้องมีบอทลอยทับ

บอทนี้เป็นวิดเจ็ตบนเว็บ **คนละตัวกับบอท LINE OA** ที่ตอบในแชท LINE โดยตรง
(อยู่ใน `apps-script/LineWebhook.gs` ดู [docs/LINE_TEMPLATES.md](LINE_TEMPLATES.md))
สองตัวนี้ทำงานคู่กัน: LINE OA เป็นทางเข้าเดิม ส่วนวิดเจ็ตเว็บเป็นทางเลือกที่ไม่
ต้องแอดเพื่อน LINE ก่อน แต่ทั้งคู่แชร์ backend เดียวกัน (Google Sheet ผ่าน
Apps Script/`Api.gs` และ Sheets REST API)

## 2. เมนูทั้งหมด

เมนูหลัก 8 ปุ่ม เรียงตามความถี่การใช้งานจริงที่พบใน LINE OA (`MAIN_MENU_CHIPS`
ใน `src/components/hemato-bot/flows.ts` — **ห้ามสลับลำดับ**โดยไม่คุยกับทีมออกแบบก่อน):

| ปุ่ม | ต้องยืนยันตัวตน | ทำอะไร |
| --- | --- | --- |
| 🔍 เช็กสถานะ | ไม่ต้อง | พิมพ์เลขที่อ้างอิง (`HEM-...`) → เห็นกลุ่ม/สถานะ/วันที่ส่ง |
| 📋 เคสของฉัน | ไม่ต้อง | พิมพ์เบอร์โทร → เห็นทุกเคสที่ผูกกับเบอร์นั้น (สูงสุด 10 เคสล่าสุด) พร้อมบอกว่ามีคำตอบหรือยัง |
| 💬 อ่านคำตอบ | **ต้อง** | ยืนยันตัวตนด้วย LINE Login หรือรหัส 6 หลักทางอีเมล แล้วเห็นลิงก์เปิดอ่านคำตอบ + ปุ่มส่งสำเนาซ้ำเข้าอีเมลเดิม |
| 📅 จองนัด | ไม่ต้อง | ลิงก์ตรงไป `/book/transplant` (จองคิวพบแพทย์ปลูกถ่ายฯ กลุ่มที่ 1) |
| 🔁 เลื่อน/ยกเลิกนัด | ไม่ต้อง | ลิงก์ตรงไป `/booking` (จัดการนัดหมายที่จองไว้แล้ว) |

ทุกบับเบิลมีปุ่ม "⌂ เมนูหลัก" กลับมาที่นี่ได้เสมอ

## 3. ยืนยันตัวตนเพื่ออ่านคำตอบ

เฉพาะเมนู "💬 อ่านคำตอบ" เท่านั้นที่ต้องพิสูจน์ตัวตนก่อน เพราะเปิดเผยลิงก์ไปหน้า
คำตอบเคส (`/answer/[token]`) ซึ่งมีเนื้อหาคำแนะนำทางการแพทย์ — เลือกได้ 2 ทาง:

1. **เข้าด้วย LINE** — กดปุ่ม พาไป LINE Login (`/hemato-bot/line` →
   `/hemato-bot/line/callback`) เทียบ LINE user ID กับชีต `line_links`
   (สร้างแถวตอนพิมพ์ "ผูกบัญชี" ในแชท LINE OA — ดู `LineWebhook.gs`) เจอแล้ว
   ออกคุกกี้ยืนยันตัวตนทันที ไม่เจอก็ชวนแอดเพื่อน LINE OA แล้วพิมพ์ "ผูกบัญชี"
2. **รับรหัสทางอีเมล** — พิมพ์เบอร์โทร ระบบส่งรหัส 6 หลักไปที่อีเมลล่าสุดที่
   ผูกกับเบอร์นั้น (ใช้ได้ 10 นาที) พิมพ์รหัสกลับมายืนยัน

ยืนยันสำเร็จทางไหนก็ได้คุกกี้เดียวกัน `sibmt_bot_verified` (httpOnly, signed,
อายุ 30 วัน) — เก็บแค่ `phoneKey` ของเบอร์ ไม่เก็บ LINE user ID หรือชื่อ

## 4. โมเดลความปลอดภัยและการเปิดเผยข้อมูล

**เพดานการเปิดเผยก่อนยืนยันตัวตน** — `shapeStatus()` ใน `src/lib/bot-lookup.ts`
คืนได้แค่ 4 ฟิลด์เท่านั้น: `referralId`, `groupNumber`, `statusLabelTh`,
`submittedTh` (+ `hasAnswer` ในเมนู "เคสของฉัน") **ห้ามเพิ่มฟิลด์อื่นโดยไม่แก้
สัญญานี้ก่อน** — ไม่มีชื่อผู้ป่วย ไม่มีอีเมล ไม่มีเนื้อหาคำตอบ

**ไม่มี timing oracle ตอนขอรหัส** — `requestCodeAction` ต้องตอบเร็วเท่ากันไม่ว่า
เบอร์ที่กรอกจะมีเคสผูกอยู่จริงหรือไม่ (ถ้าตอบช้ากว่าตอนมีอีเมลจริง คนร้ายจะใช้
ความช้าเร็วเดาได้ว่าเบอร์ไหน "มี" เคสอยู่) การส่งอีเมลจริงจึงถูก "ยิงทิ้ง" ผ่าน
`waitUntil` ของ Cloudflare (`scheduleBotCodeEmail` ใน
`src/app/hemato-bot/actions.ts`) ไม่ await ผลลัพธ์

**เก็บ hash ของรหัส ไม่เก็บรหัสจริง** — คุกกี้ `sibmt_bot_code` เซ็นด้วย HMAC
กัน tampering ได้ก็จริง แต่ตัว payload เป็น base64 ที่ใครถือคุกกี้ก็ถอดอ่านได้
ระบบจึงเก็บ hash ของรหัส 6 หลักแทนตัวรหัสตรง ๆ — แต่รหัสมีแค่ 10^6
ความเป็นไปได้ ถ้า hash เป็น SHA-256 เฉย ๆ (ไม่มีกุญแจ) คนที่ขโมยคุกกี้ไปจะ
คำนวณ hash ของทุกความเป็นไปได้แบบออฟไลน์ได้หมดในไม่กี่วินาทีแล้วไล่เทียบหา
รหัสได้เลย จึงต้องเป็น **HMAC-SHA256 ที่มีกุญแจ** (`hashCode()` ใน
`src/lib/bot-code.ts` เซ็นด้วย `AUTH_SECRET` เดียวกับที่เซ็นคุกกี้) —
ไม่มีกุญแจนี้ก็คำนวณ hash ล่วงหน้าไม่ได้ ขโมยคุกกี้ไปก็ยังไม่รู้รหัส

**รวมข้อความ error กันไล่เดา referral ID** — `resendAdvice_` และ `confirmEmail_`
ใน `apps-script/Api.gs` ตอบข้อความทั่วไปเดียวกันไม่ว่าจะเป็นกรณี "ไม่พบเคสนี้"
หรือ "token/ผลลัพธ์ไม่ถูกต้อง" เพราะ `referral_id` เดารูปแบบได้
(`HEM-วันที่-เลขไล่จาก 0001`) ถ้าแยกข้อความ คนร้ายจะใช้ความต่างของข้อความ error
เป็น oracle ไล่เช็คว่ารหัสไหนมีเคสอยู่จริงในระบบ ก่อนจะไปเดา token ต่อ
(แพตเทิร์นเดียวกับ `lookupBooking_` ใน `ManageBooking.gs`)

**ห้ามเผยอีเมลปลายทางเด็ดขาด** — `sendBotCode_`, `resendAdvice_`, `confirmEmail_`
ทุกฟังก์ชันห้าม log หรือคืนอีเมลที่ระบบส่งไปกลับมาให้ client ไม่ว่าสำเร็จหรือ
ล้มเหลว (ข้อความ error กรอง pattern คล้ายอีเมลออกด้วยใน `sendBotCode_`) ฝั่งเว็บ
(`resendAnswerAction`) ก็ไม่ forward ข้อความ error ดิบจาก Apps Script ต่อให้
client เช่นกัน คงข้อความคงที่เสมอ

**จำกัดอัตราทุก action** — ทั้ง 2 ถัง (`allowBotLookup`/`allowBotCode` ใน
`src/lib/rate-limit.ts`) กันการยิงถามรัว ๆ ไล่เดาเลขที่อ้างอิงหรือรหัสยืนยัน

## 5. ธงอีเมลยังไม่ยืนยันบน dashboard

แดชบอร์ดแสดงป้าย **"⚠️ อีเมลยังไม่ยืนยัน"** ต่อท้ายเคสที่เข้าเงื่อนไข

`needsEmailFlag()` ใน `src/lib/referral-types.ts` ขึ้นธงนี้เมื่อครบทั้ง 3 เงื่อนไข:

- เป็นเคสกลุ่มที่ 2 (ขอความเห็นสูตรยา) หรือกลุ่มที่ 3 (ส่งตัวมาเคโม)
- สถานะยังไม่จบ (`!isTerminal(status)`)
- อีเมลน่าจะใช้ไม่ได้ — สองช่องอีเมลในฟอร์มกรอกไม่ตรงกัน (`email_mismatch`)
  **หรือ** ระบบเคยออกลิงก์ยืนยันให้แล้ว (`email_verify_token` ไม่ว่าง) แต่ยัง
  ไม่มีใครกดเกิน 1 วันทำการ (`email_verified_at` ว่างและ
  `elapsed_business_hours` ≥ 8) — เคสที่ส่งเข้ามาก่อนมีฟีเจอร์นี้ไม่เคยมีลิงก์
  ให้กดเลย จึงไม่เข้าเงื่อนไขนี้ ไม่ขึ้นธงเตือนเท็จ

เคสกลุ่ม 2/3 พึ่งอีเมลนี้ส่งคำแนะนำกลับ ถ้าธงขึ้นแปลว่าคำตอบอาจไปไม่ถึงแพทย์
ต้นทาง เจ้าหน้าที่ควรโทรยืนยันเบอร์แทนก่อนส่งคำตอบ

## 6. แก้ข้อความรหัสยืนยันทางอีเมลได้ที่ไหน

ข้อความอีเมลรหัสยืนยันตัวตน (หัวข้อ "รหัสยืนยัน Hemato Bot") **ฝังอยู่ในโค้ด
ตรง ๆ** ไม่ได้อ่านจากชีต `config` เหมือนบางข้อความของ LINE OA (ดู
[LINE_TEMPLATES.md](LINE_TEMPLATES.md) §0) — **แก้ข้อความได้ที่
`apps-script/Api.gs` ฟังก์ชัน `sendBotCode_`** เท่านั้น แก้แล้วต้อง deploy
เวอร์ชันใหม่ทับ deployment เดิม (ดู §7 ด้านล่าง)

> เหตุผลที่ยังไม่ทำเป็น config-driven: ข้อความนี้สั้น ไม่มีตัวแปรให้แอดมินต้อง
> ปรับบ่อยเหมือนข้อความแจ้งเตือนกลุ่ม LINE ยังไม่คุ้มความซับซ้อนที่ต้องเพิ่ม
> ถ้าจะทำให้แก้ได้จากชีต `config` ในอนาคต ใช้แพตเทิร์นเดียวกับ
> `readConfigValue_()` ใน `apps-script/Util.gs`

## 7. มือทำก่อนเปิดใช้ (go-live checklist)

ทำตามลำดับนี้ **ห้ามข้าม** เพราะแต่ละข้อพึ่งข้อก่อนหน้า:

### (a) วางโค้ด Apps Script ทับ deployment เดิม + ทดสอบ

1. เปิด Google Sheet จริง → Extensions → Apps Script
2. คัดลอกเนื้อหาไฟล์ `Api.gs`, `OnFormSubmit.gs`, `Config.gs` ฉบับล่าสุดจาก
   repo นี้ไปวางทับของเดิม (ทั้ง 3 ไฟล์เปลี่ยนสำหรับฟีเจอร์นี้)
3. Deploy → **Manage deployments** → แก้ deployment ที่ใช้งานอยู่ →
   **New version** — **ห้ามสร้าง deployment ใหม่เด็ดขาด** เพราะ URL จะเปลี่ยน
   ทำให้ LINE webhook (Messaging API) และเว็บ (`BOOKING_API_URL`) ที่จำ URL
   เดิมไว้เรียกไม่ถูกทันที ต้องไปแก้ทั้งสองที่ตามหลัง — เสี่ยงเกินจำเป็น
4. แก้ `API_VERSION` ใน `Api.gs` เป็นวันที่ปัจจุบัน + คำสั้น ๆ บอกว่าแก้อะไร
   ก่อนกด Deploy แล้วเปิด Web app URL ด้วยเบราว์เซอร์ (`doGet`) ตรวจว่าเลข
   เวอร์ชันขยับจริง
5. รัน `runSelfTest()` หนึ่งครั้ง (อ่านอย่างเดียว) ตรวจว่าหัวคอลัมน์และโครงสร้าง
   ชีตยังถูกต้อง — บทเรียนจากชีตทดสอบ ก.ย. 2569: ฟอร์มที่ถูก copy/re-link
   จะเขียนหัวคอลัมน์กลับเป็นภาษาไทย ทำให้ระบบอ่านคำตอบไม่เจอทั้งแถว
   ถ้าพบหัวคอลัมน์เพี้ยน ให้รัน `restoreFormHeaders()` กู้กลับ (มียามกันพลาด
   ในตัว จะหยุดเองถ้าโครงสร้างไม่ตรงคาด)
6. รันเช็กลิสต์ทดสอบ **บนชีตทดสอบเท่านั้น** (ห้ามทดสอบบนชีตจริง — NFR-003)
   ตามหัวข้อ "ทดสอบใน Apps Script editor (ไม่มี test runner ให้ .gs)" ใน
   [apps-script/README.md](../apps-script/README.md) หัวข้อย่อย "Hemato Bot —
   ยืนยันอีเมลตอนส่งฟอร์ม, รหัสยืนยันตัวตน, ส่งคำตอบซ้ำ (Task 5)"
   (8 ข้อ: ส่งรหัสสำเร็จ/อีเมลผิดรูปแบบ, ส่งฟอร์มทดสอบตรวจ `email_verify_token`,
   ส่งคำตอบซ้ำสำเร็จ/ไม่พบเคส, ยืนยันอีเมลสำเร็จ/token ผิด/เคสไม่มีจริง)
   หมายเหตุการตั้งชีตทดสอบ: copy ชีตจริงแล้วฟอร์มสำเนาจะเขียนหัวคอลัมน์
   กลับเป็นภาษาไทย — รัน `restoreFormHeaders()` ในชีตทดสอบก่อนเริ่มเสมอ

### (b) เพิ่มคำถาม "ยืนยันอีเมล (พิมพ์ซ้ำ)" ในฟอร์ม (ไม่บังคับ แต่แนะนำ)

ไม่เพิ่มก็ใช้งานได้ปกติ เพียงแต่จะไม่มีการตรวจอีเมลพิมพ์ผิด (`email_mismatch`)
ขั้นตอนเต็มอยู่ใน [apps-script/README.md](../apps-script/README.md) หัวข้อย่อย
"ขั้นตอนที่ต้องทำด้วยมือ — เพิ่มคำถามในฟอร์ม (ไม่บังคับ)" สรุปย่อ:

1. เปิด Google Form → เพิ่มคำถามใหม่ต่อจากช่อง "อีเมล" เดิม ตั้งชื่อคำถามว่า
   **"ยืนยันอีเมล (พิมพ์ซ้ำ)"** ประเภท short answer ตั้งเป็นคำถามบังคับ
2. เปิดชีต `referrals` → หาคอลัมน์ใหม่ที่ฟอร์มสร้าง (หัวคอลัมน์เป็นข้อความ
   คำถามภาษาไทยเป๊ะ ๆ) → เปลี่ยนชื่อหัวคอลัมน์เป็น **`referrer_email_confirm`**
3. ทดสอบส่งฟอร์มด้วยอีเมลสองช่องที่ไม่ตรงกัน → ตรวจว่าแถวใหม่มี
   `email_mismatch = yes`

### (c) LINE Developers Console — เพิ่ม Callback URL

Web widget ใช้ **LINE Login channel** คนละอันกับ **Messaging API channel**
ของ LINE OA (แต่ต้องอยู่ **provider เดียวกัน** ใน LINE Developers Console
ถึงจะผูกกับ OA เดียวกันได้):

1. เปิด https://developers.line.biz/console → เลือก provider เดียวกับที่
   สร้าง Messaging API channel ไว้ (ดู [LINE_TEMPLATES.md](LINE_TEMPLATES.md))
   → เลือก **LINE Login channel**
2. ไปแท็บ **LINE Login** → ช่อง **Callback URL** → เพิ่ม (ไม่ใช่แทนที่ ถ้ามี
   URL อื่นอยู่แล้ว เช่นของหน้า `/login`):
   ```
   <site>/hemato-bot/line/callback
   ```
   แทน `<site>` ด้วยโดเมนจริงที่ deploy (เช่น `https://sibmt-refer.pages.dev`)
3. บันทึก แล้วทดสอบตามข้อ (e) ด้านล่าง

### (d) Deploy เว็บ

```bash
npm run cf:deploy
```

ไม่ต้องตั้งค่า secret ใหม่ — Hemato Bot ใช้ `AUTH_SECRET` (เซ็นคุกกี้ยืนยัน
ตัวตน เดียวกับ session dashboard), `BOOKING_API_TOKEN`/`SITE_URL` (เรียก
Apps Script) และ `LINE_LOGIN_CHANNEL_ID`/`LINE_LOGIN_CHANNEL_SECRET` ที่ตั้ง
ไว้แล้วสำหรับ `/login` ชุดเดิม (ดู [docs/DEPLOYMENT.md](DEPLOYMENT.md))

### (e) Smoke test บน staging/production

**ทดสอบใน demo ไม่ได้** — `npm run dev:demo` ตั้ง `AUTH_SECRET=` (ว่างเปล่า)
โดยตั้งใจ ทำให้ทุก action ที่เกี่ยวกับการยืนยันตัวตนตอบ "ระบบยืนยันตัวตนยังไม่
พร้อมใช้งาน" ทันที และไม่มี Apps Script ให้ส่งอีเมลจริง (ไม่มี `MailApp` บนเครื่อง
ตัวเอง) จึงต้องทดสอบ end-to-end บน environment ที่ตั้งค่าจริงแล้วเท่านั้น:

- [ ] **flow รหัสทางอีเมล** — เปิดเว็บ กด "💬 อ่านคำตอบ" → "รับรหัสทางอีเมล" →
      พิมพ์เบอร์ของเคสทดสอบที่มีอีเมลจริง → ต้องได้อีเมลรหัส 6 หลักจริง
      (ตรวจกล่องขาเข้า+จดหมายขยะ) → พิมพ์รหัสยืนยัน → ต้องเห็นรายการเคสพร้อม
      ปุ่ม "เปิดอ่านคำตอบ"/"ส่งสำเนาเข้าอีเมลเดิม" กดส่งสำเนาซ้ำแล้วตรวจว่าได้
      อีเมลจริงอีกฉบับ
- [ ] **flow LINE ที่ผูกบัญชีไว้แล้ว** — เตรียมบัญชี LINE ทดสอบ 1 บัญชีที่เคย
      พิมพ์ "ผูกบัญชี" ในแชท LINE OA ไว้แล้ว (มีแถวในชีต `line_links`) เปิดเว็บ
      กด "💬 อ่านคำตอบ" → "เข้าด้วย LINE" → ยืนยันบนหน้า LINE → ต้องเด้งกลับมา
      ที่เว็บพร้อมข้อความ "ผูกบัญชี LINE กับเบอร์นี้เรียบร้อยแล้ว" และเห็น
      รายการเคสทันทีโดยไม่ต้องกดอะไรต่อ
- [ ] ทดสอบเบอร์/บัญชีที่ **ไม่มี** เคสหรือยังไม่ผูกบัญชี — ต้องได้ข้อความ
      ทั่วไป ("ยังไม่พบเคสที่ผูกกับบัญชีนี้" / ชวนผูกบัญชี) ไม่ใช่ error ดิบ
