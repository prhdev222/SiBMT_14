# Hemato Bot — chat widget ถามตอบบนเว็บ (rule-based)

วันที่: 2026-09-03 · สถานะ: รอผู้ใช้รีวิว

## เป้าหมาย

แพทย์ต้นทางคลิกมาสคอต Hemato Bot (`docs/Hemato_bot.png`) บนเว็บ แล้วทำได้ครบใน
แชทเดียว: เช็กสถานะเคสทุกกลุ่ม (1–4), ดูรายการเคสของตัวเอง, อ่านคำตอบกลุ่ม 2/3,
ไปจอง/เลื่อน/ยกเลิกนัด fellow (กลุ่ม 1), และขอเปลี่ยนอีเมลปลายทางโดยกวนแอดมิน
น้อยที่สุด

## ไม่ทำ (non-goals)

- **ไม่มี LLM** — เป็น decision tree ล้วน ผู้ใช้กดปุ่มเลือก พิมพ์เฉพาะข้อมูล
  (เลข HEM-, เบอร์โทร, รหัส, อีเมล)
- **ไม่ deploy เว็บใหม่** — อยู่ใน Next.js app เดิมบน Cloudflare
- **ไม่สร้างฟอร์มจองซ้อนในแชท** — จอง/เลื่อนนัดพาไปหน้า `/book/transplant` และ
  `/booking` ที่มีอยู่
- **ไม่เปิดเผยข้อมูลเกินที่ LINE bot เปิดเผยอยู่แล้ว** ต่อคนที่ยังไม่ยืนยันตัวตน
  (กลุ่ม/สถานะ/วันที่เท่านั้น — ไม่มีเนื้อหาคำตอบ ไม่มีข้อมูลคลินิก ไม่บอกอีเมล)
- **ไม่ใช้ SMS OTP** ในเฟสนี้ (ประหยัด ~1,500 บาท/ปี) — ออกแบบจุดเสียบไว้ให้
  สลับเข้ามาแทนการ์ดแอดมินได้ภายหลังโดยไม่รื้อ flow

## ภาพรวมเมนู

| เมนู | กลุ่ม | พฤติกรรม |
|---|---|---|
| เช็กสถานะเคส | 1–4 | พิมพ์เลข HEM- → กลุ่ม + สถานะ + วันที่ส่ง + ขั้นถัดไปตามกลุ่ม |
| เคสทั้งหมดของฉัน | 1–4 | พิมพ์เบอร์โทร → รายการเคส (สูงสุด 10 ล่าสุด) พร้อมสถานะ |
| อ่านคำตอบ | 2, 3 | ยืนยันตัวตนครั้งแรกครั้งเดียว → อ่านในแชทได้เลย (ดูข้อ C) |
| จองนัด fellow | 1 | คำถามคัดกรอง 1–2 ข้อ → พาไป `/book/transplant` |
| เลื่อน/ยกเลิกนัด | 1 | พาไป `/booking` (มีเลื่อน+ยกเลิกครบแล้ว) |
| นัด OPD ทั่วไป | 4 | อธิบายการจองเองผ่าน QR / Siriraj Connect |
| เปลี่ยนอีเมลปลายทาง | 2, 3 | flow กึ่งอัตโนมัติ แอดมินกดปุ่มเดียว (ดูข้อ G) |
| ติดต่อแอดมิน | — | ช่องทางเดิม (`/contact`) |

## ส่วนประกอบ

### A. ตัว widget (Next.js, client component)

- ปุ่มมาสคอตลอยมุมขวาล่าง ทุกหน้า public (ไม่แสดงใน `/dashboard`)
- กดแล้วเปิดแผงแชทสูงไม่เกิน ~70vh บนมือถือ ปุ่มเมนูเป็น chip กดได้
- state ของบทสนทนาอยู่ฝั่ง client ทั้งหมด (decision tree) — ฝั่ง server มีแต่
  action ที่ถูกเรียกเป็นครั้ง ๆ
- ทุกจุดมีปุ่ม "เริ่มใหม่" และ "ติดต่อแอดมิน" เป็นทางหนีตาย

### B. เช็กสถานะ / รายการเคส (server actions)

- อ่าน sheet ผ่าน `referral-repository` เดิม
- เปิดเผยเท่า LINE bot: เลข HEM-, กลุ่ม, สถานะ (label ไทย), วันที่ส่ง
- rate limit ด้วย `rate-limit.ts` เดิม: ค้นด้วยเลข HEM- เพดานเดียวกับ LINE,
  ค้นด้วยเบอร์โทรเพดานต่ำกว่า (เบอร์เดาง่ายกว่า — ตามเหตุผลเดียวกับ
  `lineCasesLookupAllowed_`)
- ไม่ยืนยันหรือปฏิเสธอีเมลปลายทางในทุกข้อความ

### C. อ่านคำตอบในแชท (กลุ่ม 2/3)

หลัก: อีเมลที่ลงทะเบียนคือหลักฐานความเป็นเจ้าของเพียงชิ้นเดียว จึงต้องเปิดอีเมล
**หนึ่งครั้ง** เพื่อยืนยัน หลังจากนั้นไม่ต้องอีก

1. ผู้ใช้เลือก "อ่านคำตอบ" → พิมพ์เบอร์โทร
2. ระบบส่งรหัส 6 หลักไปอีเมลที่ลงทะเบียนกับเบอร์นั้น (ไม่บอกว่าอีเมลอะไร —
   หลักการเดียวกับ flow ผูกบัญชี LINE ใน `LineWebhook.gs`) ผ่าน endpoint ใหม่ใน
   Apps Script (`Api.gs`) ที่ห่อ logic เดิมของ `sendLinkCodeEmail_`
3. กรอกรหัสถูก → เว็บออก signed cookie (โครง `session.ts` เดิม) อายุ 30 วัน
   ผูกกับ phone key
4. จากนั้น: เปิดแชทจากเบราว์เซอร์เดิม → รายการเคส → เคสที่ตอบแล้วกด
   "อ่านคำตอบ" → เว็บดึงผ่าน `answer_token` ใน sheet แล้วแสดงลิงก์
   `/answer/[token]` ให้กดอ่านได้ทันที
5. ปุ่มรอง: "ส่งสำเนาเข้าอีเมลเดิม" (เหมือน resend ของ LINE) มีเสมอ
   สำหรับคนที่ไม่อยากยืนยัน

รหัสหมดอายุ 10 นาที, จำกัดการขอรหัส (กัน spam อีเมลคนอื่น), cookie เพิกถอนได้
โดยลบฝั่ง client

### D. จอง / เลื่อนนัด

- ไม่มี logic ใหม่ — แชทถามคัดกรอง (เช่น "เป็นเคสส่งต่อเพื่อพบแพทย์
  transplant ใช่ไหม") แล้วส่งออกไปหน้าเดิมพร้อม context ที่กรอกแล้วถ้าทำได้
- เหตุผลที่ไม่ทำในแชท: `BookingFlow` มีตรรกะ slot/cap 2 คนต่อ fellow ต่อวัน
  ครบและผ่านการใช้จริงแล้ว การทำซ้ำ = ดูแลสองที่

### E. กลุ่ม 4 + ติดต่อแอดมิน

ข้อความแนะนำ + ลิงก์ตามหน้า `/refer/[type]` เดิม ไม่มี logic ใหม่

### F. กันอีเมลผิดตั้งแต่ต้นทาง

ฟอร์มกลุ่ม 2/3 เป็น Google Form (คุมหน้าตาไม่ได้) จึงใช้:

1. เพิ่มคำถาม "ยืนยันอีเมล (พิมพ์ซ้ำ)" ใน Google Form —
   `OnFormSubmit.gs` เทียบสองช่อง ถ้าไม่ตรงตั้งธง `email_mismatch`
2. `OnFormSubmit.gs` ส่ง "อีเมลยืนยัน" ทันทีหลังส่งเคส มีลิงก์กดครั้งเดียว →
   บันทึกคอลัมน์ใหม่ `email_verified_at`
3. dashboard: เคสที่ยังไม่ยืนยันภายใน 24 ชม. (หรือ mismatch) ขึ้นธง
   "⚠️ อีเมลยังไม่ยืนยัน" ให้ resident เห็น**ก่อน**เขียนคำตอบ จะได้ทวง
   ช่องทางอื่นตอนเคสยังสด

คอลัมน์ใหม่เข้าถึงด้วยชื่อ header ผ่าน `headerMap_()` ตามกติกาเดิมของ repo

### G. เปลี่ยนอีเมลปลายทาง (แบบ B — แอดมินคลิกเดียว)

1. แชทเก็บหลักฐานครบชุด: เลข HEM-, เบอร์โทร, อีเมลใหม่, คำถามความเป็นเจ้าของ
   (ชื่อโรงพยาบาลต้นทาง, เดือนที่ส่งเคส)
2. ระบบเทียบกับ sheet อัตโนมัติ แล้วส่งการ์ดสรุปเข้า LINE แอดมิน (ช่องทาง
   admin เดิมของ bot): "เบอร์ตรง ✓ รพ.ตรง ✓ เดือนตรง ✓ — [อนุมัติ] [ปฏิเสธ]"
   ปุ่มส่งข้อความกลับเข้า webhook เดิม (`handleAdminReply_` ขยายรับคำสั่งนี้)
3. อนุมัติ → อัปเดตอีเมลใน sheet + ส่งแจ้งเตือนไป**อีเมลเดิม**
   ("เคส HEM-xxx ถูกเปลี่ยนอีเมลปลายทาง หากไม่ใช่ท่าน ติดต่อ...")
4. คำขอเก็บในชีตใหม่ `email_change_requests` (audit trail: ใครขอ เมื่อไร
   หลักฐานอะไร ใครอนุมัติ)
5. จุดเสียบอนาคต: แทนขั้น 2 ด้วย SMS OTP ได้โดยไม่แตะขั้นอื่น

เหตุที่ไม่อนุมัติอัตโนมัติจากคำถามความเป็นเจ้าของ: คนถือสำเนาใบ refer ตอบถูก
ทุกข้อ มันพิสูจน์ "เคยเห็นเอกสาร" ไม่ใช่ "เป็นเจ้าของเคส"

## แบ่งงานฝั่งไหนบ้าง

- **Next.js**: widget UI, server actions (สถานะ/รายการ/ขอรหัส/ยืนยัน/อ่านคำตอบ/
  ยื่นคำขอเปลี่ยนอีเมล), cookie session, rate limit
- **Apps Script**: endpoint ส่งอีเมลรหัส, endpoint ยื่น/อนุมัติคำขอเปลี่ยนอีเมล,
  อีเมลยืนยันตอน submit, ธง dashboard, การ์ด LINE แอดมิน + ขยาย
  `handleAdminReply_`
- **Google Form**: เพิ่มคำถามยืนยันอีเมล (แอดมินทำมือ มีคู่มือใน docs)
- **Sheet**: คอลัมน์ `email_verified_at`, `email_mismatch` + ชีต
  `email_change_requests`

## ความปลอดภัย (สรุป)

| ข้อมูล | ใครเห็น | เงื่อนไข |
|---|---|---|
| กลุ่ม/สถานะ/วันที่ | ใครก็ได้ที่รู้เลข HEM- หรือเบอร์ | rate-limited |
| เนื้อหาคำตอบ | เจ้าของเคสเท่านั้น | ยืนยันรหัสจากอีเมลลงทะเบียน (ครั้งเดียว/เครื่อง) หรือเปิดจากลิงก์ในอีเมล |
| อีเมลปลายทาง | ไม่แสดงให้ใครเห็นเลย | — |
| เปลี่ยนอีเมล | ต้องผ่านแอดมินอนุมัติ | หลักฐานเทียบอัตโนมัติ + แจ้งอีเมลเดิมทุกครั้ง |

## การทดสอบ

- dev ด้วย `mock-referrals` เดิม (`dev:demo`) ครบทุก flow ของ widget
- ทดสอบจอมือถือ (ผู้ใช้หลักเปิดจากมือถือ) + font-size control ที่เพิ่งทำ
- Apps Script: ทดสอบ endpoint ใหม่กับ sheet ทดสอบก่อน แล้วค่อยชี้ production
- เคสลบ: รหัสผิด/หมดอายุ, เบอร์ไม่พบ, เคสไม่มีอีเมล, rate limit ชน,
  คำขอเปลี่ยนอีเมลที่หลักฐานไม่ตรง
